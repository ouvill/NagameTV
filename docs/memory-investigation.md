# 選局時のメモリ増加の調査（2026-09-06）

対象: `main` の `b731a3d`。データ放送なし。製品コード・`build/mirakurun-viewer`は変更していない。

## 現時点の結論

選局に伴うRESの増加の一部は、解放済み領域をglibcが保持することによる。検証プロセスでは、再生を続けたまま診断用の`malloc_trim(0)`を一度呼ぶと、約118 MiBのRESが減った。これは当該領域が解放可能だったことを示すが、全領域についてリークがないことの証明ではない。

元の視聴プロセスではRES約690 MiB、PSS約635 MiBを確認した。短時間の再現試験で、この元プロセスの増加全体の原因を特定できたとはしていない。

別に、番組更新ストリームの10秒タイムアウト・5秒後の再接続を実測した。実況には受信キュー上限・キャンセル・世代分離の改善余地がある。

## 測定条件

- Ubuntu / Qt 6.10.2 / GStreamer / NVIDIA RTX 4070 Ti。実際のX11表示とPulseAudioへの接続を検出・検証した。
- 元の視聴プロセスは操作・停止せず、別の実表示プロセスを使用。1440×900。初期試験は字幕と画面上の流れる実況を無効にし、実況の受信自体は有効。後続の試験で字幕・流れる実況も有効にして比較。
- 検証用の別worktreeに、操作指示・`mallinfo2`の記録・診断用の`malloc_trim`を追加した。製品への定期trim導入ではない。
- RESは`/proc/PID/smaps_rollup`のRSS、PSS・FD数・スレッド数も取得。MiB=1,048,576 bytes。
- 第1試験はGStreamer leaks tracerを使用、第2試験以降は使用していない。トレーサーや診断処理の負担、他プロセスとの共有、放送内容の時間変化があるため、絶対値は単純比較しない。
- 数秒待つ試験に加え、利用者の操作に合わせ、下部のチャンネル一覧を開き、実際のカードのクリックハンドラーを通して高速切り替えを行った。

第1試験では、使用中ヒープ（`mallinfo2.uordblks`）は再生開始時約254 MiB、30回切り替え後約258 MiBだった。一方、glibc内の空き領域（`fordblks`）は約110→188 MiBになった。これらの値はglibc管理分の指標であり、Qt・ドライバー等を含むRES全体の内訳を完全に説明するものではない。

GStreamerの生存オブジェクト数は開始時748、30回切り替え後728。各時点で`GstSoupHTTPSrc` 1、`GstTSDemux` 1、`GstGLContextGLX` 1、`GstGLBufferPool` 2を維持した。`GstPad`は53、`GstTask`は8。停止後の生存総数は309で、保持して再利用するパイプラインもあるため、この数をそのままリーク件数とは扱わない。

地上波9局: NHK京都、NHK大津、Eテレ大阪、びわ湖放送、MBS、KBS京都、ABC、関西テレビ、読売テレビ。各局約3秒待ち、計27回の切り替えを実施。実況先は`jk1`だけでなく`jk2`、`jk6`等にも遷移し、履歴は各接続の初期100件程度へ置き換わった。FD数は76〜79で、周回ごとに増え続ける様子はなかった。

## チャンネル・番組情報

対象: `rust/src/network.rs`、`rust/src/player.rs`、`rust/src/epg.rs`、`qml/Main.qml`。

- HTTPクライアントは共有・再利用され、アイドル接続はホストあたり4本、保持90秒。チャンネル更新は`loading_channels`で同時実行を抑えている。
- EPGは`Arc<EpgSnapshot>`を新しいスナップショットへ置換する構造。過去の全取得結果をリストへ蓄積する実装ではない。
- 実データは69サービス、15,292番組、`/api/programs`のJSON約10.17 MiB。`fetch_services`で`programs.clone()`を行うため、EPG格納用と番組表構築用が一時的に重複する。番組表用のQStringListも別に保持する。
- 毎秒の`refresh_current_programs`はネットワーク通信なし。ただし文字列や配列の再生成は行う。
- 通常HTTP用の「リクエスト全体10秒」のクライアントを番組更新ストリームにも使っている。検証ログで`TimedOut`と15秒間隔の再接続を繰り返すことを確認した。イベント受信待ちが5秒間発生し、継続接続として機能していない。
- 初期化時に通知抑制の基準時刻を設定し直す。通知判定は受信チャンクの非空白判定で、JSONイベント単位ではない。curlで受信した開始文字`[`だけでも条件上は対象になるが、今回のアプリの再取得ログは実イベントのチャンクがトリガーだった。開始文字が毎回の再取得原因だとは結論しない。
- 番組表のLoaderは画面上の列範囲を絞っているが、`guideOpen`を条件にしていないため、非表示でも一部の項目を保持する。これは意図的な保持に相当し、リークとは別に使用量を減らせる点。

改善候補: ストリーム専用のタイムアウト・キャンセル設計、イベント単位の解析と再接続をまたぐ更新抑制、EPG全体の不要なclone削減、非表示画面の保持方針の明示。

## 実況

対象: `rust/src/comments.rs`、`rust/src/player.rs`、`qml/Main.qml`。

- 京都・大津はともに`jk1`。`restart_comments`は同じ実況先なら接続を再作成しない。この2局の往復が実況接続を毎回増やす構造ではない。
- 表示履歴は200件に制限されている。流れるコメントはアニメーション終了時に`destroy()`される。
- ただし受信からUIまでの`mpsc::channel()`は上限なし。UIが選局等で止まる時間に入力が集中すると、履歴200件とは別にキューが増える。`try_iter().collect()`も1回で全量を処理する。
- 切り替えは世代番号で停止を要求するが、タスクのJoinHandle/AbortHandleは保持していない。WebSocket接続・送信・closeには明示的な期限がなく、その待機中は即座にキャンセルされない。
- キュー上の`CommentEvent`には世代番号がない。旧接続から既に投入されたコメント・状態を、切り替え後の画面が受け取る可能性がある。受信ループ内の世代確認だけでは防ぎ切れない。
- 同一実況先への再接続を省く判定は、終了したタスクかどうかを確認していないため、切断後の再接続にも改善余地がある。

改善候補: 件数と本文サイズに上限のあるキュー、1回のUI処理数の上限、イベントに世代を付与して受信側でも検証、接続タスクの明示的なキャンセルと接続・終了期限。これらの不足が今回の約700 MiBの主因だったと確認したわけではない。

## 字幕と流れる実況の表示

別プロセスで、実放送の字幕と実際のNX-Jikkyoコメントを有効にした。60秒の連続表示、10回のオン／オフ、無効化後15秒の待機を実施。実況履歴は初期104件から約138件まで増えた程度であり、大量投稿時の負荷を再現した試験ではない。

- 流れるコメントの表示Item数は0〜6で増減し、無効化後の待機で0になった。`onFinished`による破棄がこの条件で機能している。
- 字幕の文字項目は0〜34で入れ替わり、古い字幕が文字数として累積する様子はなかった。
- ただし`subtitlesEnabled=false`でも字幕のTS抽出・解析・`pollSubtitles`・JSON生成は継続し、QMLのRepeaterも最新の字幕で更新される。無効化後も26文字、さらに後で12文字の項目を確認した。表示を隠すだけである。
- 流れるコメントには同時表示数の明示的な上限がなく、受信イベントが集中すると多数のLabelとアニメーションを作る。通常の表示寿命は有限でも、瞬間的な使用量の上限は必要。

改善候補: 字幕を隠している間の描画Item・アウトライン生成を遅延し、最新の字幕データだけ保持する。実況の同時表示数と最大文字数を制限する。大量実況、長時間視聴、連続したウィンドウサイズ変更等での字体・描画キャッシュの増加は別途測定が必要。

## 優先順位と未確定事項

1. 番組更新ストリームの10秒タイムアウトを分離し、接続・切断・更新通知を適切に扱う。
2. 実況のキュー上限・世代付きイベント・明示的キャンセルを入れる。
3. 字幕・番組表など非表示UIの保持を減らし、全番組のcloneを避ける。
4. 同じ番組・画面サイズ・操作履歴で長時間の対照試験を行い、必要ならネイティブの確保元を追跡する。

利用者の元プロセスは約690〜720 MiBで、今回の新規プロセスでは約550 MiBまでの増加を観測した。元プロセスに対して強制GC・trim・デバッガ呼び出しは行っておらず、そのメモリのうち何MiBが解放済みかは未確認。したがって、今回の結果から「リークなし」「原因はすべてキャッシュ」とは結論しない。今回のローカル試験は地上波9局で、BSの再現試験は含まない。
