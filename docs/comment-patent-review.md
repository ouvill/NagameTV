調査日: 2026-09-18。対象: `a2afdcd16e12aaaaa9769604c7744fbfde09df65` の実装。
日本の特許を対象に、公開された登録公報の請求項とソースコードを照合した。

## 1. 一覧と移動弾幕の併用

7080382の請求項1、7277651の請求項1は、ネットワークから取得した動画と他端末のコメントを扱い、
動画とは別の領域にコメントを一覧表示し、その少なくとも一部を移動表示するプログラムに関する。
7080382では動画との重なりも要求される。7277651には端末装置・方法の独立請求項もある。
このため、サーバを自作・運営していないという事情だけでは、端末側の請求項を除外できない。
[7080382・請求項1](https://patents.google.com/patent/JP7080382B2/ja#C1)、
[7277651・請求項1/11/14](https://patents.google.com/patent/JP7277651B2/ja#C1)。

| 照合する要素 | コードで確認した事実 |
| --- | --- |
| ネットワーク経由の動画受信・表示 | Mirakurunから受信するライブ映像を `GstGLQt6VideoItem` に表示する構成 |
| 他端末から投稿されたコメントの受信 | [features/comments.rs](../rust/src/features/comments.rs) 56–59行でNXのコメントWebSocketを設定 |
| 動画とは別の一覧領域 | [Main.qml](../rust/qml/Main.qml) 665–679行の右側サイドバー、[ProgramSidebar.qml](../rust/qml/ProgramSidebar.qml) 232–240行の `CommentList` |
| 一覧と弾幕でコメントが共通する | [player/comments.rs](../rust/src/player/comments.rs) 135–153行で受信コメントをリプレイへ、176行で同じ受信集合を一覧モデルへ渡す |
| 動画と重なる移動表示 | [Main.qml](../rust/qml/Main.qml) 295–333行の弾幕レイヤーと、[danmaku.rs](../rust/crates/viewer-comments/src/danmaku.rs) 613–650行の横移動 |

特にライブ視聴中に実況一覧を開く利用形態で対応が明瞭になる。
一覧は受信履歴、弾幕は映像時計に同期した表示なので、常に全件・同時刻で一致するわけではない。
ただし、請求項の対象は一覧の「少なくとも一部」のコメントであり、この違いだけで除外できるとは判断しない。

**衝突判定を削除するだけでは、この組み合わせへの対応は残る。**
一覧を普段は閉じているという説明も、一覧を開けるプログラム自体の検討を不要にはしない。
7277651の請求項7は一覧の表示切り替えも扱っている。
[7277651・請求項7](https://patents.google.com/patent/JP7277651B2/ja#C1)。

## 2. コメント同士の衝突回避と時刻同期

4695583の請求項1/9は、コメントの受信・時刻付き記憶・再生時刻に対応する読み出しと、
移動コメントを含むコメント同士の重なり判定・表示位置調整を組み合わせる。
従属項3/11は、表示時間と文字幅に応じた速度、および先行コメントへの追いつき判定をさらに扱う。
[4695583・請求項](https://patents.google.com/patent/JP4695583B2/ja#C1)。

対応する実装は [viewer-comments/src/danmaku.rs](../rust/crates/viewer-comments/src/danmaku.rs) にまとまっている。

| 処理 | 場所 | 動作 |
| --- | --- | --- |
| 表示中コメント同士の分離判定 | `Active::separate_from()`、186–199行 | 現在時点と両者が存在する終端時点の横位置・文字幅を比較 |
| 後続コメントの追いつき判定 | `Active::admits()`、202–223行 | 間隔、相対速度、先行コメントが消えるまでの時間を比較 |
| 重ならない行の探索 | `Engine::measured()`、628–650行 | 判定を通る行を探し、行番号に応じた縦位置で生成 |
| 文字幅に応じた速度 | 同、605–616行 | 表示秒数を設定し、速度を `(viewport.width + width) / seconds` で算出 |
| フォント変更時の再配置 | `Engine::relayout()`、413–470行 | 再計測後に衝突する場合、別の行を探す |
| 再生時刻に応じた投入 | `load()` / `seek()` / `next_due()`、662–706行 | 時刻順の保持、シーク後の復元、再生位置に達したコメントの読み出し |

製品画面は [Main.qml](../rust/qml/Main.qml) 303–315行で `playbackClock` と `update_timeline()` を使う。
通常の同期表示では `Start::At` → `separate_from()` の経路になる。
`admits()` だけを変更しても、製品の同期表示や文字サイズ変更時の衝突回避は残る。

時刻については、[replay.rs](../rust/src/features/comments/replay.rs) 208–227行が受信コメントのUTC日時を
`ClockReading::media()` で映像の相対位置へ変換し、`time` と本文を組にして弾幕へ渡している。
ライブ・録画・タイムシフトに共通するため、「受信した瞬間に表示するだけ」の実装ではない。

ただし、以下は一致が未確定の要件として残す。

- NXの日時からクライアント内で計算した位置と、公報の「コメント付与時間」との対応。
  受信データの `vpos` をそのまま映像の再生位置として使っているわけではない。
- サーバがコメントを受信する都度、配信・受信するという要件。ライブWebSocketと過去ログの一括取得は分けて評価する。
  [protocol.rs](../rust/crates/viewer-comments/src/protocol.rs) 48–57行は初期履歴とその後のライブ更新を購読するが、
  それだけでNXサーバ側の全挙動を立証したことにはならない。

2018年のFC2事件第一審でも、4695583のこの配信・受信要件が争点になっている。
本アプリの評価では「重なりを避けている」ことだけで請求項全体の充足を断定しない。
[東京地裁平成28年(ワ)38565・判決本文](https://www.courts.go.jp/assets/hanrei/hanrei-pdf-88073.pdf)。

## 3. システムとしての弾幕表示

6526304の請求項2は、動画サーバとコメントサーバを分けた構成を明示している。
請求項5/6は文字列の長さに応じた速度や一定の表示時間を追加する。
7178462の請求項2/3にも、サーバが分かれた構成、文字列が長いほど速い表示、一定の表示時間がある。
[6526304・請求項2/5/6](https://patents.google.com/patent/JP6526304B2/ja#C1)、
[7178462・請求項2/3](https://patents.google.com/patent/JP7178462B2/ja#C1)。

本アプリの表示時間と速度式はこれらと技術的に近い。
MirakurunとNX-Jikkyoが別サーバであること自体は、請求項2を避ける根拠にならない。
一方、NXへの投稿者が家庭のテレビ等を見ていた場合、そのコメントが「当該動画配信サーバからの動画」を
視聴中に付されたものといえるかは、コードだけでは確定できない。
複数端末、投稿時点の動画、サーバから送信される時間情報、開発者・利用者・サーバ運営者の行為を別途照合する。

6526304の請求項3/4には、受信コメント情報が表示継続時間を含むという追加要件がある。
本実装では継続時間をクライアント側で決めるため、その要件の一致は今回確認できなかった。
ただし、その追加要件を持たない請求項1/2が別に存在する。

同系列の [7153786・請求項1](https://patents.google.com/patent/JP7153786B2/ja#C1) は
一覧と移動表示を含むシステムも対象とするため、1節の端末側特許と併せて確認対象にする。

## 4. 映像外の余白に流れるコメント

4734471の請求項1/7/9では、時刻同期に加え、コメント表示領域が映像表示領域と部分的に重なり、
映像の外側にもコメントを表示する構成が焦点になる。
衝突回避は請求項6の追加要件であり、衝突回避を外すだけで独立請求項を避けられるわけではない。
[4734471・請求項](https://patents.google.com/patent/JP4734471B2/ja#C1)。

[Main.qml](../rust/qml/Main.qml) 295–299行は、弾幕の幅を `video.width`、高さを
`Math.min(video.height, width * 9 / 16)` にする。
高さを制限しても、実際の映像が左右の余白を伴って縮小表示されるときの幅は制限していない。
[DanmakuOverlay.qml](../rust/qml/DanmakuOverlay.qml) 27行の `clip: true` も、この弾幕領域でのクリップになる。

`qml6glsink` のアスペクト比維持は既定で有効で、
[playback.rs](../rust/src/playback.rs) 195–199行ではこれを変更していない。
[GStreamer公式・force-aspect-ratio](https://gstreamer.freedesktop.org/documentation/qml6/qml6glsink.html#qml6glsink:force-aspect-ratio)。

例えば映像部品が1280×600、映像が16:9なら、実映像の幅は約1067で左右に約107ずつ余白ができる。
一方、弾幕領域は1280×600のままなので、コメントの進入・退出時に余白を通過する計算になる。
これはソースと既定動作からの推定であり、今回GPUを使った表示確認は実施していない。
放送映像自体に焼き込まれた黒帯と、プレイヤーが映像外に作る余白は区別する必要がある。

対策案は、映像の実際の表示矩形に弾幕の位置・幅・高さ・クリップを合わせること。
ただし、この変更だけでは1〜3節の別の請求項との対応は残る。

## 5. 投稿UIと新しい分割特許

2026年4月28日発行の7852687は、右側のコメント表示、動画下方の投稿欄・速度入力欄、送信ボタン等の
配置を組み合わせるプログラムの請求項を持つ。
[7852687・請求項1](https://patents.google.com/patent/JP7852687B2/ja#C1)。

本アプリには右サイドバー、下部の投稿UI、送信操作、速度設定がある。
ただし [PlaybackSettings.qml](../rust/qml/PlaybackSettings.qml) 25–29行は操作ボタンの上に開くPopupであり、
投稿UIも [Main.qml](../rust/qml/Main.qml) 563–575行で再生面の下端に重ねる配置になる。
「動画表示欄の下方」という要件を満たすか、各部品が請求項にいう画面として成立するかは未確定。
今後、常設の動画下部ツールバーに整理する際は再確認する。

投稿時の `vpos` は [posting/protocol.rs](../rust/crates/viewer-comments/src/posting/protocol.rs) 120–133行で
現在の実時刻とセッションの基準時刻から計算する。これをそのまま再生中の映像経過時間だと評価していない。

## 実装方針を決めるための候補

| 変更候補 | 減らせる対応関係 | 残る検討 |
| --- | --- | --- |
| 移動弾幕を取り除き、映像外の通常のコメント一覧に限定 | 今回の主要候補に共通する移動・重畳表示の要素を大きく減らす | 時刻同期や一覧に関する別特許まで含めた非侵害を保証するものではない |
| 弾幕を実映像矩形内にクリップ | 4734471の映像外表示という要素 | 衝突回避、一覧との併用、システム系の候補 |
| 弾幕と共通するコメント一覧の機能を取り除く | 7080382、7277651等の一覧併用という要素 | 4695583、4734471、6526304等 |
| 衝突判定・追いつき回避・衝突に基づく再配置を取り除く | 非重複制御を要求する請求項の要素 | 一覧併用・映像外表示。文字サイズ変更や復元の経路も対象にする必要がある |
| 表示速度を文字幅によらない値にする | 文字幅依存の速度を要求する限定 | 広い独立請求項は残るため、これだけの変更を回避策としない |

これは設計変更の検討表であり、いずれか一つを実施すれば安全という表ではない。
