# ライブコメントの受信・保持の見直し

2026-09-27実装。ライブコメントは視聴セッション内のメモリーに保持し、巻き戻しに利用する。
録画向けの取得・永続キャッシュは[実況過去ログの取得・保持仕様](comment-archive-redesign.md)を参照。

確認済みの利用要件は次のとおり。

- ライブ映像を巻き戻したときも、その場面のコメントを再表示する。
- コメント履歴は現在の視聴中だけ保持し、視聴終了後は残さない。
- ライブの巻き戻しでは過去ログAPIによる補完を行わない。
  NX-Jikkyoなど別の取得元による追加の履歴取得も設けない。

タイムシフトで再生できるのは、その視聴セッションで受信して保持している映像である。
実況が有効なら、一時停止中や巻き戻し再生中も最新のコメントを受信し続け、
対応する映像と一緒に見返せるようにする。視聴開始前の時間帯を取得する要件はない。
通信切断や実況OFFによってコメントを受信できなかった区間は欠落として扱い、
映像が残っていることだけを根拠にコメントの取得済み・0件を判断しない。

この要件から、ライブの受信履歴と録画用の永続過去ログを分離する。
ライブの最新表示・巻き戻しは、その視聴セッションで受信したコメントだけを参照する。
録画用キャッシュに同じ時間帯のコメントがあっても混ぜない。
ライブでのシーク、一時停止、復帰、再接続、表示切り替えを理由に、過去ログ取得を開始しない。
通常のWebSocket購読で届く初期履歴は受信データに含めるが、巻き戻しのための追加要求は出さない。

録画ファイルの再生では、従来どおり過去ログAPIと永続キャッシュを利用する。
録画からライブへ切り替えた時点で送信済みの録画用要求は、既存の完了・回復規則に従って扱う。
その完了結果をライブ表示へ混ぜず、ライブ側の受信・保持・表示を待たせない。

保持期間は[映像のタイムシフト](ts-input-implementation.md)に合わせる。
映像の保存方式とコメントの保存方式を同一にすることは要件にしない。

| 場面 | コメントの受信・表示・保持 |
| --- | --- |
| 最新位置を視聴 | 受信を継続し、保存処理や過去ログDBの状態を待たずに新着を表示する |
| 一時停止 | 表示時計も停止する。受信と履歴への追加は継続する |
| 巻き戻し・遅延再生 | 再生位置のコメントを履歴から表示する。今届いた新着を遅れた映像に重ねない |
| タイムシフト無効 | 現在の表示と、受信・映像の時刻差を扱うための有限なバッファーを持つ |
| 一時停止時のみ保持 | 停止直前から表示中のコメントを引き継ぎ、映像の保持開始に合わせて履歴を残す |
| 一時停止時のみ保持からライブへ復帰 | 復帰完了を確認して、見返せなくなった映像に対応する履歴を解放する。現在表示に必要な分は残す |
| 常に保持 | 映像を見返せる範囲の履歴を維持し、ライブへ復帰しても保持する |
| 映像の保持範囲が縮小 | 見返せなくなった古い履歴を解放する。保持範囲の先頭で表示を復元するための余裕は残す |
| 弾幕表示OFF | 新着の表示は止める。実況が有効なら受信し、映像の保持方針に従って履歴を維持する |
| 実況機能OFF | 受信を停止する。既に受信した履歴は映像の保持範囲に従って維持する |
| 実況機能を再度ON | 受信を再開する。OFF中の欠落を追加取得で埋めない |
| 選局・再生停止・視聴終了 | その視聴セッションの履歴と表示状態を破棄する。再起動後の再利用は行わない |
| 同じ視聴中の通信再接続 | 保持済み履歴を維持する。接続の切れ目を区別し、再配送された同一コメントの二重表示を避ける |

コメントには元の投稿UTC、出典、識別情報、本文・表示属性、自分の投稿かどうかを保持する。
映像の時計区間と投稿UTCから再生位置を求める。時計の不連続をまたいで外挿せず、
新しい視聴セッションへ古い局・ソースのコメントを渡さない。
履歴は到着順だけで管理せず、遅着や順序の入れ替わりがあっても対象時刻を検索できる構造にする。

最新位置で遅れて届いた新着を現在位置から表示する処理と、巻き戻し時に投稿時刻で再表示する
処理は区別する。最新表示の都合で元の投稿時刻を書き換えない。
接続直後の履歴をすべて「今来た新着」として一斉に表示しない。
映像の時計が未確定のコメントは有限な待機領域で扱い、PCの現在時刻で対応を決めない。

保持の先頭には、現在の表示仕様に合わせて16秒の復元余裕を設ける。
通常視聴中も現在表示中のコメントを保持し、一時停止した瞬間に必要な履歴が消えないようにする。
表示件数の制限と巻き戻し用履歴の保持範囲は分ける。
同文という理由だけで別投稿を削除せず、再接続時の再配送と本来の複数投稿を区別する。

視聴セッションがQtに依存しないRustの[履歴ストア](../rust/src/features/comments/replay/history.rs)を所有し、
受信バッチの追加、時計の確定、表示範囲の検索、保持範囲外の解放を担当する。
メモリー保持を基本とし、更新をコメント到着・時計区間の確定・保持境界の変更に集約する。
表示のポーリングごとに履歴を全走査したり、同じ保護範囲を全置換したりしない。

保持期間は映像の設定に従い、コメント専用の保持時間・容量設定は追加しない。
件数による履歴の上限は設けず、異常な流量に備えて内部の予算を256 MiBとする。
本文・識別情報・時計キーの長さに、B-treeのノード、未使用スロット、管理情報の余裕を加えた
保守的な見積もりで管理する。上限を超えた場合は古い再生位置の履歴から解放し、受信を続ける。
容量超過は標準エラーへ警告し、失った区間を過去ログAPIで補完しない。

Linux/glibcの機器不要テストでは、日本語40文字（UTF-8で120バイト）のコメント6万件を
保持した際のヒープ割当増分が38,968,464バイト（約37.2 MiB）、予算上の見積もりが
62,700,000バイト（約59.8 MiB）だった。測定は`mallinfo2().uordblks`の差分であり、
アプリ全体のRSSやすべての本文長・投稿密度を保証する値ではない。
この入力では256 MiBの予算に約25万件が収まる。表示用の件数・容量制限を履歴へ流用しない。
一時ファイルへの退避やユーザー向けの容量設定は、メモリー保持で不足する根拠が得られた場合に検討する。

未確定の映像時計を待つ領域は、履歴予算の内側で4 MiB・120秒に制限する。
確認済みの時計区間に入るまで表示へ投影せず、時計の巻き戻りで対応が曖昧な投稿も投影しない。
時刻の対応には投稿UTCと映像時計だけを使い、待機期限の管理とは分離する。
再配送の重複判定は出典・スレッドと投稿番号・投稿UTCで行う。
識別番号のない投稿は、本文が同じでも別投稿として保持する。

映像の保持範囲が一時停止位置より先に進んだ場合は、停止中の画面の16秒分も保護する。
その画面と新しい保持範囲の間にある、再生できなくなった区間は解放する。
最新位置での一時的な表示時刻と元の投稿時刻は別に管理し、自分の投稿という情報も引き継ぐ。

ライブ経路を共有SQLiteから外し、次の処理を削除した。

- `live_comments`へのINSERT、時計対応UPDATE、保持範囲外DELETE。
- API補完のための`live_coverage`の検索・更新。
- 過去ログを保護するためのライブ範囲の`pins`更新。
- 最新表示・巻き戻しのための、ライブ履歴と永続過去ログを結合するSELECT。
- ライブ専用のDBセッション登録、死んだセッションの回収、チェックポイントと容量整理。

録画用SQLiteの整理やI/Oに失敗しても、ライブ側の受信キューを止めない。
過去ログ取得の`Demand`は録画メタデータだけを受け付け、ライブの範囲は型が異なるため渡せない。
互換性のため旧`live_comments`・`live_coverage`テーブルは残すが、新しい受信データは書き込まない。
旧データは録画キャッシュを開いた際の死んだセッションの回収で解放される。
ライブのコメント欄を開くだけではDBを起動しない。設定画面で保存容量を確認・整理する操作は、
録画キャッシュの明示的な利用として扱う。
ライブの受信障害や容量超過は、操作と原因を`tracing`で標準エラーへ記録する。
欠落が起きた区間を完全に受信できたものとして扱わず、診断に本文・ユーザーIDを出さない。
欠落からの復旧は通常の受信再接続で行い、過去ログ補完へ切り替えない。

受入条件は次のとおり。コアの検証はQtを起動しないRustテストで行う。

| 条件 | 確認する結果 |
| --- | --- |
| ライブ視聴開始、最新位置の表示 | ライブ機能のために録画用DBを開かず、過去ログHTTPを送らない |
| 一時停止後に新着を受信し、再開・巻き戻し | 受信を継続し、それぞれの映像時刻で再表示する |
| 連続シーク、ライブ復帰、表示OFF/ON | 過去ログへの追加要求と永続キャッシュ参照が0件 |
| コメント切断、再接続、実況OFF/ON | 受信済み履歴を利用し、欠落の補完要求と再配送の二重表示がない |
| 投稿時刻の遅着、映像時計の不連続 | 最新表示用の時刻調整が履歴を変更せず、未確認区間に誤投影しない |
| 映像の保持開始・範囲縮小・復帰完了 | 表示復元分を残しつつ、寿命を終えた履歴を解放する |
| 選局・停止・終了 | 旧履歴を解放し、新しいセッションに混入させない |
| 録画用DBのI/O失敗 | 起動済みワーカーが失敗しても、ライブの新着受信、表示、履歴検索が影響を受けない |
| 録画ファイル再生 | 録画用の取得・永続キャッシュが従来の契約を満たす |

`python3 scripts/test.py app viewer-comments`で、アプリ419件、コメントライブラリー106件と
型の誤用を拒否するdoctestを確認した。保持・順不同受信・重複・自分の投稿フラグは
`proptest`でも照合する。録画の回帰試験では、WAL書き込みロック中のキャッシュ読み出し、
録画要求の送信後にライブへ切り替えても保存が完了することを確認した。
実GPUと専用PipeWire出力を検証した隔離環境で、`python3 scripts/test.py danmaku startup`も
成功した（QML部品343件、製品Main.qmlの起動・タイムシフト試験）。
SQLxの44クエリー、アプリとコメントライブラリーのClippy、製品QML全92ファイルの検査も通過した。

この変更はライブ仕様の見直しであり、先に確認した録画用キャッシュの削除候補検索や
定期整理の問題は別途修正する。ライブとの分離だけで、それらのSQLが改善されたとは扱わない。
