# デインターレース設定と動画統計の移植

## インターレース判定と適用状態（2026-09-26）

動画統計は入力の走査方式、設定したデインターレース方式、現在の適用状態を分けて表示する。
`mixed`では「混在」に加え、直近の入力フレームがインターレースかプログレッシブかを示す。
方式はYADIF、Linear、OpenGL vfir、VA-API adaptiveで、処理を省略しているときは
「適用なし」、Off設定では「無効」とする。有効な設定でも、フレーム未取得や停止中は「—」を表示する。

入力・出力のcapsは更新時に
[`GstVideoInfo`](https://gstreamer.freedesktop.org/documentation/video/video-info.html)へ変換する。
走査方式・画素形式・寸法・fps・PARを型付きで取得し、省略された走査方式とPARには
GStreamerの既定値を使う。`mixed`のフレーム判定には`INTERLACED`と`ONEFIELD`を使う。
単一フィールドも補間が必要な入力として扱う。`fields`と`alternate`を含め、
プログレッシブと確認できたフレームだけをOpenGL処理の省略対象にする。
フラグの意味は[GStreamerの走査方式の仕様](https://gstreamer.freedesktop.org/documentation/additional/design/interlaced-video.html)を参照。

適用状態は直近の入力フレーム、出力形式、GPUフィルターのpassthrough状態から判定する。
GPU経路ではフィルター自身の状態を優先する。[VA-API](https://github.com/GStreamer/gstreamer/blob/main/subprojects/gst-plugins-bad/sys/va/gstvadeinterlace.c)は`mixed`のプログレッシブフレームでも
処理を継続する場合があり、入力の走査方式だけでは省略中と判断できない。
1秒ごとの観測であり、表示中のフレームと一対一には対応しない。
表示する方式名は選択中の処理方式で、GStreamer内部の形式依存の代替方式や、
テレシネ処理・末尾処理で使われる補助アルゴリズムまでは示さない。
probeが保持するのは形式と直近の判定だけで、映像bufferや画素、履歴を保持しない。
シークではフレーム判定を、ストリーム開始では形式も破棄し、READY/NULLでは統計に公開しない。

## 実況コメント表示中の動画更新（2026-09-25）

コメントの計算と状態管理をRust、表示をQMLへ戻し、動画アイテムをシーングラフ同期の
直前に更新対象にする修正を加えた。描画専用C++への移行だけでは症状を解消できず、
利用者の保守性に関する方針に合わせて運動モデルをRustへまとめた。
[現在の責務分担](comment-display-redesign.md#rustとqmlの分担)と
[比較計測・検証結果](comment-frame-pacing.md)を参照。
影を無効にした同じAV1で、Waylandの動画更新は横流れ21.95→29.69 fps、
ポップ22.07〜23.53→29.49〜29.89 fpsとなった。Xwaylandでは元から約30 fpsで大きな差はなかった。
利用者から滑らかさの改善報告を得た。画面提示と音声出力の時刻差は未計測。

以下は実装を検討した順序で残した調査記録であり、専用描画の説明は現在の実装ではない。

## 追加調査（2026-09-24）

専用描画への変更後も症状が残るとの報告を受け、動画のPTSを含む追加計測を行った。
Waylandでの描画モードの違いと、動画アイテムの同期直前の更新に改善の手掛かりがあった。
測定結果と次の実装案は[実況表示中のフレーム更新](comment-frame-pacing.md)を参照。
以下は専用描画を導入した時点と、それ以前の記録。

追加の確認で、利用者は普段から影を無効にしていることが分かった。
影だけの最適化では解決しないため、コメント専用のシーングラフ描画へ変更した。
当時の実装では、責務と時計・保存画像の扱いも専用描画へ合わせて変更した。

コメントごとのQMLオブジェクト・座標通知と、保存画像用の全コメントの毎フレームJSON化を廃止した。
文字ノードを再利用するため、影が無効な場合にも適用される変更。

専用Xwayland画面・RTX 4070 Tiで、横流れとポップの位置更新がGUIスレッドでは実行されず、
時刻だけを進めたときに文字ノードを再生成しないことを部品試験で確認した。
停止、シーク復元、モード変更、文字サイズ変更、長いコメントの影も検証した。
製品画面と保存画像では、ポップの位置・傾き、1080p・4:3・非正方画素、
画面サイズ変更、連写、シークを含む試験が成功した。
通常版のQML試験326件・評価版346件、製品Main.qmlの起動試験、接続・デスクトップ連携試験、
Rust試験333件（任意5件は未実施）、両構成のClippy、QML全91ファイルの静的検査が成功。
配布用ビルドも更新した。この変更後の画面提示間隔の改善量は未計測であり、
描画処理の移動と、利用者の物理画面での滑らかさの解消は区別する。

以下は、専用描画への変更前に座標通知の重複だけを減らした段階の記録。

利用者の再確認により、継続的な滑らかさの低下は実況コメントを表示しているときに
発生し、横流れ・ポップ表示の両方、特にポップ表示で目立つことが分かった。
sinkの破棄は0でも、Qtでの動画とコメントの合成や画面への提示が遅れる可能性がある。
sinkのカウンターだけでは、画面上で全フレームを表示したかは判断できない。

再生同期用の`DanmakuController::advance`は、1フレームの処理中に全コメントの
座標を3回通知していた。さらに、新着コメントの文字幅計測が同期で戻るたびに、
既存コメントの座標を再通知していた。期限の更新と座標通知を分離し、期限切れの削除と
新着の生成を終えた後に、各コメントの最終位置を1回だけ通知するよう変更した。
軌道、表示件数、影、再生時計は変更していない。

専用Wayland画面、RTX 4070 Ti、1920×1080表示で、同じAV1録画に毎秒6件の

横流れで平均約0.43 msから0.33 ms、ポップで約0.49 msから0.38 msへ減った。
一方、開始3秒を除いたQtの画面更新間隔の中央値は、横流れが26.9 msから26.7 ms、
ポップが26.0 msから25.8 msで、大きな改善は確認できていない。sinkの破棄は全条件で0。
影やスクリーンショット用の状態取得を省いた診断でも、画面更新間隔の差は小さかった。
これらの機能は製品では維持し、計測用コードは`build/comment-cadence-*`へ退避した。

横流れ・ポップ表示について、新着の生成を伴う更新、期限切れ、後方シークでの復元時に
通知が重複しないことをQMLテストで確認した。部品テストは326件成功、評価用18件は
対象外。製品のMain.qmlを使う起動テストも成功した。描画負荷の削減と、利用者の環境での
体感上の解消は区別する。専用画面での計測は物理画面の提示品質を保証しない。

検証中の再ビルドで`media_caption.h`が生成先の異なる2経路から読み込まれ、
関数の二重定義でコンパイルが失敗した。`#pragma once`をインクルードガードへ変更し、
生成先が異なっても同じ定義を重複させないようにした。
接続・デスクトップ連携テスト、Rustテスト333件（任意5件は未実施）、通常構成と

## EPGStation経由のAV1録画の滑らかさの調査（2026-09-24）

「2026年07月01日18時30分00秒-２０２６ＦＮＳ歌謡祭　夏…_av1_nvenc.mp4」で、
NASから開く場合に比べ、EPGStation経由では継続再生中の滑らかさが落ちるとの報告を調べた。
動画は1440×1080、29.970 fps、progressiveの10bit AV1とAAC。
HTTPとSMBから取得した先頭64 MiBのSHA-256は一致した。

冒頭60秒分の圧縮映像・音声を、現行HTTP Readerと同じ512 KiB単位の取得方式で
GStreamerのdemuxerへ供給した。88回のRange要求で44 MiBを取得し、処理は約2.3秒、
HTTP応答の待ち時間は合計約1.8秒だった。この測定では平均転送速度に余裕がある。
直近4範囲を保持するキャッシュも試したが、このファイルでは要求回数が変わらなかったため、
製品コードへの変更は採用していない。

Workshopの専用画面、RTX 4070 Ti、PipeWire仮想出力を検証してから、製品のMain.qmlで
同じ冒頭部分を比較した。GStreamer 1.28.2の既定NV12表示ではP010からの色変換が
`not-negotiated`で失敗したため、比較時は全経路でGPU表示形式をRGBAに明示した。
この色変換エラーはローカルでも発生し、報告された経路間の差とは区別する。

ローカル比較用のファイルは、取得した先頭64 MiBを元のバイト位置・ファイル長で保持した
疎ファイルである。比較は取得済みの冒頭35秒に限定し、SMBをマウントした状態での
アプリ再生とは区別する。ローカル、HTTP URL、EPGStationの録画一覧からの再生は、
いずれも`nvav1dec`、29.970 fps、RGBA出力となり、35秒間のsinkの破棄は0だった。
継続再生中の1秒ごとの観測では、映像キューは全経路で8フレームを保持していた。

現行の512 KiBキャッシュへ戻した比較でも、全経路でsinkの破棄は0だった。
開始後5秒を除き、描画スレッドで計測したQtの`frameSwapped`間隔は次のとおり。

| 入力 | 中央値 | 95パーセンタイル | 最大値 |
| --- | ---: | ---: | ---: |
| ローカルの比較用ファイル | 54.3 ms | 80.6 ms | 98.0 ms |
| HTTP URL | 51.3 ms | 76.6 ms | 96.6 ms |
| EPGStationの録画一覧 | 52.0 ms | 78.2 ms | 91.8 ms |

全経路で画面更新の間隔にばらつきがあり、HTTPだけが遅くなる傾向は見られなかった。
これは専用Xwayland上の35秒ずつの観測であり、物理画面の表示品質や動画の実効fpsを示す値ではない。

この時点の比較では経路間の差の原因を特定できなかった。その後の実況コメント表示の
調査は上記を参照。sinkの破棄が0でも、
物理画面への提示間隔が均等であることは保証しない。普段の起動条件・表示先で、
差が出る同じ場面の統計を揃えて比較する必要がある。調査コード・ログはGit対象外の

## 実装

mainのplayback.rsとvideo_stats.rsの契約を移植し、処理別に分割した。

- `playback/deinterlace.rs`: 起動設定をMode enumへ検証し、映像処理elementを生成。
- `playback/video_output.rs`: sinkの形式を検証し、CPU／NVDEC／VAのメモリー制約を持つ出力binを構築。
- `playback/stats.rs`: 現在のcaps・sink統計・queue使用量を読み取り、所有するスナップショットを返す。
- `player/statistics.rs`: Qt境界でJSONへ変換。変換失敗はログへ記録する。
- `qml/VideoStats.qml`: 1秒ごとに値を更新するパネル。固定の11行を再利用し、更新ごとにdelegateを作り直さない。

## デインターレース

`NAGAMETV_DEINTERLACE=yadif|linear|off|gl|va`を起動時に指定する。既定はyadif。
GPU経路、NV12表示、デコーダー／メモリー形式の統計は[GPU映像処理](gpu-video.md)を参照。
mainと互換のquality・balanced・disabled、前後空白と大文字にも対応する。
不正な値は型付きエラーとして起動を失敗させる。実行中には変更しない。
Offはidentityを使い、YADIF/Linearはauto・all fieldsで処理する。

[公式deinterlace資料](https://gstreamer.freedesktop.org/documentation/deinterlace/index.html)では、
autoは入力のinterlace情報に応じた処理、all fieldsは両フィールドの出力となる。
これは入力が常にインターレース、または常に出力fpsが倍になるという保証ではない。

## 統計とメモリー

パネルのLoaderを有効にした時だけTimerを生成する。閉じるとLoaderがパネル・Timer・
最後のスナップショットを破棄する。Rustには統計用Timerや履歴、frameの参照を持たせない。
[Qt Loader](https://doc.qt.io/qt-6/qml-qtquick-loader.html#active-prop)に基づく。

入力・出力解像度、fps、走査方式、PAR、画素形式、deinterlace設定、sinkのrendered/dropped/
average-rate、queueのbuffer数・byte数・時間、GStreamerバージョンを表示する。
READY/NULLでは以前のcapsやフレーム数を表示しない。未知値・非有限値は「—」とする。

sinkは[GstBaseSink stats](https://gstreamer.freedesktop.org/documentation/base/gstbasesink.html#GstBaseSink:stats)、
queueは[current-levelプロパティ](https://gstreamer.freedesktop.org/documentation/coreelements/queue.html)を読む。
sinkの集計は画面への実表示回数ではなく、queue時間は放送からの遅延ではない。
この環境ではsink average-rateがcapsのfpsと大きく異なる小さな値になる場合があり、
実際の表示fpsとして解釈しない。ネイティブが返した値を診断情報として表示している。

## mainの統計パネルとの表示差の補完

mainの表示領域寸法／DPR行と閉じるボタンを追加し、左16px・最大幅510px・
操作部の表示に追随する縦位置、背景・枠・角丸・余白・文字サイズを移植した。
項目名と説明はmainの既存翻訳カタログへ接続し、平均レートのfps単位も補完した。
カード内のクリックは背後の映像操作へ渡さず、閉じるボタンは通常の子コントロールとして扱う。

寸法は映像Itemのwidth/height、DPRは同ItemのScreen.devicePixelRatioへのバインディング。
