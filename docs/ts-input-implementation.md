# 共通TS入力とライブ振り返り

2026-09-17。録画とライブの既定入力を、元TS → tsreadexライブラリー →
GStreamer appsrc → playbin3へ変更した。録画全体の変換ファイルは作成しない。
[設計](ts-input-design.md)と[従来の比較](tsreadex-trial.md)を引き継ぐ実装。

## 操作と保持範囲

- ライブでも一時停止、10秒戻し、30秒送り、シークバーを利用できる。
- バーは現在保持している範囲。遅れ時間を表示し、「ライブに戻る」で最新付近へ移動して再生する。
- 設定 →「タイムシフト」でオン／オフ、メモリー／一時ファイル、容量・保持時間を選び「適用」。
  再生設定からも開ける。ライブ視聴中の変更は入力を再起動し、古い保持を破棄してライブ位置へ戻る。
- 初期値はメモリー。最大30分か256 MiBの早い方。一時ファイルは最大30分か2 GiB。
  容量は各16～65,536 MiB、時間は1～180分で指定できる。古いTSから破棄し、
  メモリーは次の分割領域を確保する前にも上限を確認する。
  索引・番組情報は別に16 MiBまで、appsrcキューは約94 KiB、入力単位は188×256バイト。
  これはTS保持の上限であり、映像・音声デコーダーを含むアプリ全体のメモリー上限ではない。
- 選局・停止で保持を破棄する。再接続は保持を残して別区間として追記する。
- 一時停止位置が期限を過ぎても画面を維持する。再開操作で通知して現在の保持範囲の先頭へ移動する。
  一時停止中も受信と破棄は継続し、消えた場面は飛ばす。
- 無効でもtsreadex経由。受信と再生の間には最大2 MiB／2秒の有限バッファーを置く。
- 受信開始前には戻れない。実況の過去ログ同期は別機能。遅延中の映像に新着の弾幕を重ねない。

LinuxのFS保存先は `$XDG_CACHE_HOME/mirakurun-viewer/timeshift`、未指定時は
`~/.cache/mirakurun-viewer/timeshift`。約1 MiBずつ分割し、古い分割を削除する。
読み書きに必要なファイルだけ開くため、保持時間に比例してFDを開き続けない。
正常終了で削除し、異常終了したセッションは次のFS利用時に掃除する。
セッションのファイルロックを取得できる場合だけ掃除し、別の起動中インスタンスは保持する。
掃除と新規セッションの登録は共通のロックで直列化し、同時起動による誤削除を防ぐ。

## 時刻と番組情報

元TSのPCRと映像PESのPTSを索引化し、PAT/PMTを各開始点に保持する。
時刻のラップ・巻き戻りを扱い、時計の不連続は別区間として記録する。PMT変更では
PAT/PMTの索引を更新し、tsreadex自身に構成変更を追従させる。シークは同じReaderを借用した
`SeekPlan`から実行し、フィルターを作り直す。元TS位置と変換後サイズは混ぜない。
字幕と文字スーパーはCLIの `-c 5 -u 5` 相当で補完する。音声補完は有効にしない。

appsrcへはPCR単位のバッファーと対応する時刻を渡す。境界では不連続を通知し、
demuxに直前のPESを排出させる。TIME seekの要求番号をsegmentへ引き継ぎ、
既存の「新しいsegmentと出力を確認する」完了判定を維持した。

EIT/SDT/TOT/TDTは元TSで解析し、再生位置に対応したスナップショットを選ぶ。
受信中の最新情報で巻き戻し中の番組を上書きしない。字幕は変換後のTSから解析し、
flush時に旧状態を破棄する。録画は188-byte TS、192-byte M2TS、204-byte TSの入力に対応する。

録画は先頭・末尾を各約2 MiBだけ先に読み、PCRから概算の長さと全体のシーク範囲を公開する。
概算は長さに `≈` を付ける。指定先が逐次索引の範囲外なら、PCRとファイル位置を補間して
その付近のPAT/PMT/PCRを優先探索する。最大12回、各約2 MiBの探索で開始点を選び、
通常の先行デコードへ渡す。要求受付はUI上でディスクI/OやReaderロックを待たず、
入力スレッドが取消し世代を読み取り単位ごとに確認する。番組情報は探索地点でも元TSから取得し、
追加の観測は16件か1 MiBまで保持する。探索中はバックグラウンドの逐次読み取りを譲る。

全体を逐次探索した後は確定した長さへ切り替える。先頭・末尾で時計の不連続を検出した素材は
概算を公開せず、逐次探索済みの範囲を使う。後から途中の不連続が見つかった場合も概算を取り下げる。
したがって任意の編集TSで、全体未探索のまま正確な長さ・全位置の時刻を保証するものではない。
実行中のOS読み取り自体は中断できず、低速NASの実機での待ち時間は別途確認が必要。
長いGOPや字幕管理情報の再送が少ない録画は、先行読み出し
だけで任意位置の完全復元を保証できず、実放送素材による追加検証対象。

### NHKの約16秒停止と長時間録画（2026-09-17）

利用者指定の2026年09月15日21時「ニュースウオッチ９」を検証。拡張子はm2tsだが
188バイトTSで、6,943,738,264バイト。約14.806秒で字幕、約14.979秒で第2音声がPMTに追加され、
主映像・主音声・PCRのPIDは変わっていなかった。

冒頭64 MiBをCPU限定の `recording-output-audit.py` で比較した結果:

| 入力 | 観測 |
| --- | --- |
| 元TSをplaybin3へ直接入力 | 約16.714秒で止まり、期限内にEOFへ到達せず |
| tsreadex `-n -1` | 約16.498秒で止まり、期限内にEOFへ到達せず |
| tsreadex `-n -1 -c 5 -u 5` | 約40.528秒のEOFへ到達、映像1175・音声1875バッファーをデコード |

PMT変更ごとのフィルター初期化を止めるだけでは改善しなかった。字幕・文字スーパーを
補完してから製品の実GPU・音声出力で確認し、28秒まで継続、20秒／10秒への一時停止シークが成功。
全6.94 GBのファイルでも同じ確認と、全体探索完了前の2,893,457 ms（約48分13秒）への移動が成功した。
概算長は3,616,822 ms。これは全編を再生した検証や音声の聴取確認ではない。
元TSと診断ログは無視対象の `benchmark/timeshift-fixes/` に置き、放送内容を試験fixtureに含めない。

再現コマンドは `bash scripts/test-startup.sh recording-probe PATH`。
ハードウェアを検出・検証し、製品画面で28秒の出力進行と境界前後・長い録画の遠方シークを調べる。
機器不要の回帰試験では、補完PMT／字幕データ、探索の読み取り量と取消し、時計リセット時の概算拒否、
容量を繰り返し超えた保持領域と期限切れ再開を確認する。

最終再試験では再生開始の5秒待ちがタイムアウトした。診断状態を表示するよう試験を補強したが、
次の実行は事前の `pactl info` が `Connection failure: Connection terminated` を返して停止した。
AGENTS.mdの機器要件に従い、音声接続復旧まで再生試験をいったん中断した。
直前のタイムアウトと音声接続断の因果関係は未確定。上記のNHK成功結果は、それ以前の実行結果である。
通常の製品起動・タイムシフト試験とQML215件は、この切断前に成功している。

利用者による再起動後、表示・GPU・PulseAudio接続と出力先の検証を再実行し、すべて成功した。
最終コードで同じ全6.94 GBの録画を再試験し、再生開始、28秒間の出力進行、
20秒／10秒／2,893,457 msへの一時停止シークが成功した。遠方シーク時も長さは概算の状態で、
全体探索完了を待たずに移動できた。再生・シークのエラーはなく、前回の開始タイムアウトは再現しなかった。
ログは `benchmark/timeshift-fixes/broadcast-after-restart.log`。実際の聴取と全編再生、NAS実機での
応答速度は今回も検証していない。前回タイムアウトの原因自体を特定したものではない。
