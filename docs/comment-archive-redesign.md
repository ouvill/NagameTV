# 実況過去ログの取得・保持 再設計

2026-09-19設計、2026-09-20実装。[現在の動作の要約](comment-archive-fetch-design.md)。
以下は実装した設計と受入条件であり、末尾に実測と検証範囲を記録する。
この文書は、現行の取得単位や保存期限を前提にせず、録画再生時の要求から設計し直す。
時間・容量の既定値は、明記したAPI上限を除きアプリ側の設計値である。

## 1. 利用者に約束する動作

- 録画を開いたら、TSにある番組情報からその番組の実況をまとめて取得する。
  通常の終了済み番組は初回1要求。取得済みなら再生・シーク・再起動で再取得しない。
- 実況のために録画ファイル全体を読み出さない。ネットワーク上の録画でも、
  再生で読むデータと、量を制限した補助読取りだけで動作する。
- シーク先の局と時計が分かり次第、保存済みコメントを表示に渡す。
  通信の待機時間を、キャッシュ読出しに適用しない。
- コメントは投稿日時どおりに再生する。件数や通信頻度を抑えるために保存段階で間引かない。
- 「未取得」「取得結果が0件」「放送直後で未反映の可能性」「同期情報なし」「通信失敗」を区別する。
- キャッシュを削除しなくても、旧実装が作った細切れの取得範囲を補完できる。

初回の未取得番組は、提供元の応答と保存完了を待つ時間がある。
初回も一定秒数以内に全コメントが出るとは保証しない。
取得待ちを繰り返さないことと、キャッシュがあるシークの待ち時間を短くすることを分けて検証する。

## 2. 旧実装から改めた点

| 旧実装の構造 | 問題 | 新しい方針 |
| --- | --- | --- |
| 全編走査の完了で録画全体の取得範囲を確定 | 遅いストレージでは追加の全ファイル読取りが続く | 番組情報で取得を計画。同期情報は再生位置で確認 |
| 未確定時は現在位置から30分先読み | 暫定修正であり、番組全体の取得完了を扱えない | 番組単位を基本とし、番組情報がない場合だけ固定枠を使う |
| 保存済みの各区間を厳密に避け、穴ごとに要求 | 数秒のキャッシュが多数あるとHTTPが細分化する | 同じ取得対象内の穴を包む1区間を要求。重複取得を許容 |
| 放送直後の成功を1時間おきに失効させる | 再生中ずっと再確認が起こり得る | 保存済みデータは常に利用。翌日以降の確認は1回だけ |
| 約1秒おきのJob作成でもLoadingになる | HTTPを送っていない判定処理まで取得中に見える | 需要・期限の変化で計画し、HTTPと保存の実状態を表示 |
| 256MiB・区間数・未使用日数で削除 | 断片化が削除の判断にも影響する | 容量を基準に番組・固定枠単位で整理。日数だけで消さない |

実装上の確認箇所は、[TS入力](../rust/src/playback/input/mod.rs)、
[実況への範囲受渡し](../rust/src/playback/input/source.rs)、
[取得計画](../rust/crates/viewer-comments/src/cache/download.rs)、
[保存判定](../rust/crates/viewer-comments/src/cache/store.rs)、
[ワーカー](../rust/crates/viewer-comments/src/cache/worker.rs)。
EITの開始日時・継続時間は[番組解析](../rust/src/transport/programs.rs)に既にある。

提供された`benchmark/cache.sqlite3`の読取りでは、jk4の取得済み区間は18区間、
合計294秒、保存コメントは291件だった。録画本編114分を取得済みではない。
これはコピー時点のDBの状態であり、現在のアプリの通信実績や提供元の総コメント数を表さない。

## 3. 取得と同期は別の情報を使う

| 情報 | 用途 | これだけでは分からないこと |
| --- | --- | --- |
| TSの対象サービスと実況局の対応 | 取得する実況チャンネルの決定 | 録画内の全区間が同じサービスか |
| EITの現在／次番組、開始日時、継続時間 | 番組の取得予定範囲 | 実際の録画開始・終了、映像位置との対応 |
| TOT/TDTとPCR、連続性の観測 | 現在の映像時刻と投稿UTCの対応 | 未読部分の時計飛びや局変更 |
| ファイルの大きさ・端点PCR | 再生時間やシーク位置の概算 | 録画全体が時計的に連続している保証 |

EITだけでも局と番組日時を検証できれば取得を開始できる。
表示には、現在位置で検証した時計対応が別途必要。
EITの予定開始を「映像0秒」とみなしたり、未読区間をまたいで時計を外挿したりしない。
時計不連続では対応区間を分け、その区間で確認できたコメントだけを投影する。
既存の[Catalog](../rust/src/transport/programs/catalog.rs)のこの保証は維持する。

番組識別には対象サービスのnetwork/transport/service ID、event ID、開始日時を使う。
event IDだけ、番組名だけ、ファイル名だけでは識別しない。
録画への現在のMirakurun EPGによる補完は行わない。
実況チャンネルへ対応できない場合は取得を止め、局を特定できないことを表示する。
系列局への対応は既存の対応表を使い、ローカル番組まで内容が一致するとは保証しない。

### TSの読取り

1. 再生Readerとシーク探索が既に読んだTSから、番組・時計情報を共有する。
2. 必要な情報が足りない場合だけ、現在位置付近を補助的に読む。
   同じ位置・同じ不足情報の探索をタイマーで繰り返さない。
3. 補助SI読取りは1回8MiBまで。既存の端点調査は先頭2MiB・末尾2MiBまでとし、
   開く際の追加読取りは合計12MiB以内とする。番組の取得開始に末尾調査の完了を要求しない。
4. シーク1回の追加読取りは、位置探索とSI補完の合計32MiB以内。
   初期調査・シークそれぞれの開始から2秒を経過したら新しいI/Oを発行しない。
   SI補完へ移っても期限を延ばさない。必要な情報が揃えば予算前に終了する。
5. 読取りは再生・UIを塞がないワーカーで行う。未完了の読取りを積み上げず、
   連続シークの未着手要求は最新1件へ置き換える。

上記は追加I/Oの予算であり、通常の映像再生に必要な読取りは含めない。
OSのファイル読取り自体が停止した場合、2秒以内の強制終了を保証するものではない。
次のI/Oを出す期限と、UIが待たないことをそれぞれ保証する。
不足時は再生Readerによる後続の観測を待ち、TS終端まで探索する処理に切り替えない。

**実況の呼出し元を変えるだけでは不十分**。
通常の録画再生で起動する既存の全編走査も外し、シーク・番組表示を上記の読取りで成立させる。
一時停止したまま録画全体を読む動作を残さない。
全編を調査する診断や索引作成を将来設ける場合も、通常再生とは別の明示操作にする。

## 4. 取得対象を決める

### 番組情報がある場合

取得対象を「番組の開始〜終了に前後2分を加えた区間」とする。
余白は録画ののりしろ、シーク直後の表示復元、軽微な終了時刻訂正を吸収するための取得量であり、
録画の実際の長さや同期可能範囲ではない。
録画が番組の途中から始まっていても、その番組全体を取得してよい。

- 通常は、現在位置で観測した現在番組を選ぶ。
- 録画先頭では、現在番組が前番組の可能性がある。先頭の時計から2分以内に次番組が始まり、
  現在番組の終了と連続していれば、次番組を主対象とし、先頭を含む余白と合わせて取得する。
  次番組を選べる根拠がない場合に、ファイル名から決めつけない。
  先頭の初回計画は、選択に必要な情報が揃うか、上記の読取り予算に達した時点で作る。
  現在番組だけ先に届いたことを理由に前番組へのHTTPを先行させない。
- EITの対象サービス・CRC・current/next・日時と継続時間を検証する。
  未定義の日時・長さ、逆転、算術オーバーフローは番組計画に採用しない。
- 番組が6時間を超える場合は、番組開始に固定した6時間区間に分け、現在区間と必要な次区間だけを取得する。
  長時間特番の全量取得で初回表示や保存を過度に遅らせないためのアプリ側の上限である。
- 複数番組の録画では次番組を候補として保持し、現在の取得対象の末尾1分前から次を計画する。
  余白で見えている次番組へEITが切り替わっただけではHTTPを出さない。
  シークで取得対象外へ移った場合は、その位置の番組を計画する。
  先読み先が録画終端を越えると既知なら行わない。未読の全番組を探しに行かない。

タイトル・説明の更新やEITの再受信では計画を作り直さない。
同じ番組の終了訂正が取得済み範囲内なら追加HTTPは0件。
延長が外に出る場合は訂正を5秒間まとめてから追加部分を計画し、既存コメントを使い続ける。
予定終了を過ぎても現在番組のままで、有効な終了訂正がない場合は固定枠で補う。
短縮・番組変更で不要になった保存済みコメントを、その場で削除する必要はない。

### 番組情報が足りない場合

局と現在位置のUTCが分かれば、UTCの毎時00分・30分を境界にした30分枠を使う。
表示復元分の16秒を先頭に、先読み分の2分を末尾に加える。
枠の起点を再生位置の移動ごとにずらさない。次の枠は境界2分前から取得対象にする。
実装ではこの時点で隣接する2枠を1つの対象範囲へ広げ、同じ補完規則でまとめて取得する。
UTCも分からない場合は取得せず、同期情報を待つ。

後から番組情報を得たら番組単位へ移り、取得済み範囲を流用する。
この場合、最初の固定枠と番組補完の計2要求になり得る。
補完済みの同じ番組へ戻るだけでは追加要求を出さない。

### 今回の録画への適用例

`2026年09月18日21時00分00秒-金曜ロードショー「ナイトミュージアム」…m2ts`は、
約14.1GB。先頭・末尾を各16MiBだけ調べた調査で、次のEITを確認した。
この16MiBは調査で読んだ量であり、EIT検出に必要な最小量ではない。

| 場所 | EIT |
| --- | --- |
| 先頭付近 | 現在20:54〜21:00、次21:00〜22:54（event 8062） |
| 末尾付近 | 21:00〜22:54の番組と、その後の番組 |

先頭の時計は20:59:52頃。新仕様では先頭付近の次番組情報を採用し、
**jk4・9月18日20:58〜22:56を通常1要求で取得**する。末尾の情報はこの計画の前提ではない。
21:40や22:30へのシークでも、同じ保存済みデータを読む。
このファイルでは初期補助読取り7,471,104バイトで現在／次番組を確認できた。
末尾の調査を含む値であり、録画全体14.1GBは走査していない。

## 5. キャッシュの穴をHTTPの単位にしない

保存の検索キーは提供元・実況チャンネル・UTC。取得計画の番組IDや録画パスとは別にする。
同じ放送を別ファイルで開いても再利用できる。
範囲はUTC秒の半開区間`[start, end)`、コメント時刻はマイクロ秒を保持する。

1. 取得対象から、利用できる取得済み範囲の和集合を引く。
2. 穴がなければHTTPは出さない。取得済みはコメントが0件だった範囲も含む。
3. 穴が複数あれば、同じ取得対象内の最初の穴の開始〜最後の穴の終了を1要求にする。
   間の保存済みデータを再受信してもよい。
4. 局・提供元が異なる対象は結合しない。番組訂正、固定枠、6時間分割でも同じ規則を使う。
5. 送信直前に他プロセスの保存完了を再確認し、不要になった要求は送らない。

| 保存済み | 取得対象 | HTTP |
| --- | --- | --- |
| なし | 20:58〜22:56 | 全範囲を1要求 |
| 数秒の区間が18個 | 同上 | 最初〜最後の穴を包む最大1要求 |
| 21:00〜22:00 | 同上 | 前後の穴を包む20:58〜22:56を1要求 |
| 20:58〜22:56 | 同上 | 0要求 |
| 20:58〜22:56 | 延長で20:58〜23:12に変更 | 22:56〜23:12を1要求 |

最後のコメント時刻やコメント件数から、取得済み範囲を推測しない。
成功した要求範囲を記録する。応答が0件でも、未要求部分まで空として埋めない。

取得元は現在の統合過去ログAPIを1つ使う。
ニコニコ実況とNX-Jikkyoの両方が対象で、同じ番組について2サービスへ別々に要求しない。
どちらかが0件でも、それだけで取得失敗や再取得理由にはしない。
統合対象、空応答、最大3日という制限は[提供元の公開仕様](https://jikkyo.tsukumijima.net/)に基づく。
内部の6時間区間は、このAPI上限とは別の判断である。
終了秒を含む[提供元の範囲処理](https://github.com/tsukumijima/jikkyo-api/blob/bca86ffe77edb61d23fdf478c9aa35faca161753/app/Models/Kakolog.php)への
変換は`endtime=end-1`。1秒の穴だけなら隣接1秒を含める。

## 6. 再取得の条件を限定する

取得済みは「その日時範囲への正常応答を保存した」という意味に限定する。
提供元には収集完了を保証する印がないため、「全コメントが確定した」とは表示しない。

| 状態 | 利用と再取得 |
| --- | --- |
| 対象終了から24時間以上後に成功 | 保存済みを再利用。時間経過だけでは再取得しない |
| 対象終了から24時間未満に成功 | 暫定保存。直ちに利用でき、毎時の再確認はしない |
| 暫定保存の対象終了から24時間が経過 | 次にその対象が必要になったとき、まとめて1回再確認。成功後は通常再確認なし |
| 正常応答0件 | 同じ時間規則で空の結果を保存。「永久にコメントなし」とは断定しない |
| 利用者の「この番組の実況を再取得」 | 対象を1回更新。旧データを表示しながら取得。連打は1件にまとめる |
| HTTP・API・JSON・保存の失敗 | 取得済みにしない。正常な旧データを維持する |

24時間はアプリが再確認を一度に絞るための基準であり、収集完了の保証ではない。
同じ取得対象の再確認予定・成功はDBに保存する。分割されたキャッシュ行ごとには発火させない。
番組未選択・実況OFF・弾幕OFF・アプリ終了中に、再確認のためだけの通信はしない。
古い録画へ戻るたびに「最終利用から1時間」などの期限を延ばす方式も使わない。

### 放送直後と録画中のファイル

取得可能な終端は当面`floor((now - 10分) / 5分) * 5分`とする。
提供元は5分おきの収集と反映遅延を案内しているが、10分で全件が揃う保証はない。
[提供元の説明](https://jikkyo.tsukumijima.net/)とアプリの余裕時間を区別する。

- 対象のうち、この終端までの範囲だけを要求・保存する。未来側は未取得のまま残す。
- 新しい終端が進み、かつ表示位置が保存終端の2分前以降に来たときだけ末尾を追加取得する。
  同じ終端への再要求はしない。追加の機会は5分境界ごとで、全番組を5分おきに確認しない。
- 対象の最終部分まで取得可能になったら、視聴中の対象に限り残りをまとめて取得できる。
- 放送直後を追いかける再生では追加取得が必要になる。終了済みの古い録画ではこの処理は発生しない。
- 暫定範囲は後日の1回の再確認でまとめ直す。将来の放送部分を空成功にして終わらせない。

## 7. 通信を起動する条件と失敗時の扱い

取得計画を動かすのは、対象番組・枠の変更、必要なメタデータの取得、未取得境界への接近、
シーク確定、待機期限の到来、手動再取得、キャッシュの変更通知。
毎フレーム・毎秒の時刻更新だけでは新しいHTTP Jobを作らない。
次の意味のある期限にタイマーを1つ設定し、DB更新通知でも再判定する。

- 未送信の需要は最新の対象へ集約し、同じ対象の送信・保存中に重ねて送らない。
- シーク中の新規HTTPだけ500ms待つ。表示用DB読出しは待たせない。
- 同じキャッシュ領域・提供元で同時HTTPは1件。送信開始は30秒以上あけ、10分に最大6件。
  これらは暴走への上限であり、「30秒ごとに取得する」という予定ではない。
- 接続5秒、応答開始・無通信30秒で失敗とする。受信が進む正常応答は一定サイズで打ち切らない。
- 通信断・5xxなどの一時障害は、初回失敗後5分、次の失敗後30分に各1回だけ自動再試行。
  対象が必要な場合に限る。失敗が続けば自動取得を止め、再試行できる状態を表示する。
- 429の`Retry-After`は提供元全体で守る。待機には0〜30秒の揺らぎを加える。
  認証・パラメーター等の非一時的4xx、不正JSON、原因不明のAPIエラーは自動反復しない。
- HTTPライブラリーによる隠れた再試行を無効にし、応答のリダイレクトも自動追従しない。
  起動中の待機は単調時計で管理し、壁時計の巻戻しで再起動後の要求枠を補充しない。
- 失敗回数・待機・送信履歴は永続化する。再生し直し、再起動、キャッシュ削除、手動再取得で
  提供元の待機を迂回しない。手動再取得は対象の自動再試行停止を解除できる。
- SQLiteや容量不足で保存できない場合は新規HTTPを止める。
  完了済み応答があればローカルで回復し、保存に失敗したからといって再ダウンロードしない。

送信済みの応答は、シーク・録画切替・表示OFF後も受信と保存を完了させ、将来再利用する。
遅れて届いたデータは現在の局・時計・ソースを照合して表示する。
アプリ終了は受信を中止できる。未完了応答を成功にせず、受信完了済みのものは次回ローカルで回復する。

## 8. 保存内容と寿命

保存は次の3層に分け、各層の上限を他の層の間引き条件に使わない。

| 層 | 保持するもの | 寿命 |
| --- | --- | --- |
| 永続過去ログ | 投稿UTC、出典、本文・表示属性、取得済み範囲、取得・確認履歴 | 再起動後も利用。容量不足時に未使用対象から整理 |
| ライブ受信履歴 | 受信したコメントと実際の受信継続区間、時計対応、自分の投稿 | タイムシフト可能なTSと、その先頭16秒前まで |
| 表示用メモリー | 現在位置の前16秒〜後2分を中心とする検索結果 | シークや局・時計変更で差し替え。必要な部分をDBから補充 |

### 永続過去ログ

- 既定の保存目標を1GiBとし、設定で変更できるようにする。
  未使用日数や区間数だけでは削除しない。取得済みの内容を期限切れ扱いにもしない。
- 整理は最終利用の古い番組・固定枠から行う。現在開いている対象と受信・取込中の対象は保護する。
  同じUTC範囲を複数対象が参照するときは、残る対象に必要なコメントを削除しない。
- 1GiBは保存データの会計上の目標であり、DBファイルの厳密な上限ではない。
  保護中の番組、ライブ保持、一時応答、SQLiteの索引・WAL等で超過し得る。
  設定には実ディスク使用量も表示する。容量不足で保存できなければ明示的に停止する。
- 未使用キャッシュの削除と、選択番組の再取得を分ける。再取得のために全キャッシュを消させない。
- 整理でデータを消した際は対応する取得済み範囲も消す。
  取得計画の完了印だけが残って、コメントなしのまま再取得できなくなる状態を作らない。

設定範囲は64〜65536MiB。保護中のデータは目標超過時にも維持する。
自動整理されない恒久保存・録画への同梱・全録画の事前取得は、この変更には含めない。

### 重複と更新

過去ログにはNX-Jikkyoとニコニコ実況の出典を保存する。
コメント番号の一意性を仮定せず、同文コメントを1件に潰さない。
時刻・出典・識別情報・内容の組合せと同一応答内の出現数を使い、
重なる応答どうしは出現数の最大を保持する。重複取得で表示件数を倍増させない。
ライブとの統合にも同じ出現数の考え方を用い、自分の投稿情報を維持する。

再取得の応答に含まれなかったことだけを、既存コメントの削除指示とは扱わない。
提供元が一時的に0件を返しても、保存済みの正常コメントを消さない。
この方針では、後日提供元から削除された投稿がキャッシュに残る場合がある。
取得日時・今回の受信件数と、保存済み件数は分けて記録する。

### 正常なデータを公開するまで

応答は一時ファイルへ逐次保存し、受信完了後にJSON全体とAPI成功を検証する。
短いトランザクションで未公開領域に取り込み、最後にコメントの統合・取得済み範囲・
確認履歴を原子的に公開する。途中で落ちても旧データを利用できる。
正常な応答を件数上限で切って「取得済み」にしたり、途中JSONを空成功にしたりしない。
一時ファイルは公開後に削除し、応答の全履歴を重複保存し続けない。

表示のDB読出しは書込みを伴わず、取込中も公開済みデータを読める。
メモリー上限に達した場合は表示周辺の読出し範囲を縮めるかページングする。
録画全体の取得・保持件数や取得済みの判定には影響させない。

## 9. ライブ・表示・診断との境界

ライブの最新位置はWebSocket受信を使い、過去ログを取りに行かない。
振り返りでは、同じ局・時計区間で連続受信・保存した範囲を利用する。
欠けた部分だけ固定枠で補い、TSの保持範囲外へは取得を広げない。
ライブ保存は録画向けキャッシュのLRU整理で落とさない。

弾幕OFFは新規過去ログ取得を止めるが、ライブ受信・保持は続ける。
実況機能OFFは受信も止める。いずれも保存済みデータは保持規則に従って残す。
録画中も弾幕スイッチは操作可能とし、取得待ちや時計待ちをスイッチの無効化で表さない。

UIでは「表示できるデータ」と「追加取得の状態」を別に持つ。
保存済みコメントを表示しながら追加取得中、という状態を正しく表す。

| 状況 | 表示例 |
| --- | --- |
| 時計・局が不足 | 実況の同期情報を確認中／実況チャンネルを特定できません |
| HTTP送信中・受信中 | 実況を取得中 |
| 受信完了、ローカル取込中 | 実況を保存中 |
| 取得結果が空 | この時間帯の取得結果は0件 |
| 放送直後の未取得部分 | 過去ログの反映待ち |
| 要求制限・失敗 | 再試行予定時刻、または再取得操作を表示 |

保存済みがあるときは、追加取得の失敗で弾幕を消さない。
現在の2分窓が空なだけで「この番組には実況がない」とは表示しない。
再生位置が変わるたびにローディング表示を点滅させない。

診断では、取得理由・対象番組・UTC範囲・HTTP回数・応答バイト数・保存件数・出典別件数、
表示対象数と除外理由、TSの追加読取り量、同期情報待ち時間を確認できるようにする。
本文やユーザーIDを診断ログへ出す必要はない。
「コメントが少ない」を取得不足・提供元の件数・表示制約に分けて調査できることを要件とする。

## 10. 実装の境界と旧キャッシュの移行

内部の責務は次の4つに分ける。録画入力にHTTPやキャッシュ整理を持たせない。

| 責務 | 入出力と保証 |
| --- | --- |
| メタデータ観測 | サービス、番組候補、現在位置の検証済み時計を公開。読取り予算を所有 |
| 取得計画 | 番組／固定枠と需要・保存状態から対象と次の期限を決定。描画の時計対応を作らない |
| 取得・保存 | 制限、通信、検証、回復、永続化を所有。正常公開前に取得済みにしない |
| 再生への投影 | 保存済みUTCを現在の時計で映像位置へ変換。新規HTTPの待機を持たない |

計画の根拠は`Program`／`TimeWindow`／`Unavailable`、
取得処理は`Idle`／`Waiting`／`Receiving`／`Importing`／`Failed`のようなenumで表す。
番組情報の有無と時計情報の有無は独立しているため、一つの「全体確認済み」boolへまとめない。
送信許可を持つ要求、受信完了、応答検証済み、公開可能な取込結果はTypestateで順序を保証する。
いずれも対象・世代・範囲を一緒に運び、別対象へ完了状態を流用できないAPIにする。

DBには既存のコメント・UTC coverageと別に、計画対象、確認方針の版、暫定確認の期限と結果を持つ。
ただし計画の完了状態は現存するcoverageと整合させ、独立した真偽値だけを信用しない。
番組のメタデータ訂正、整理、回復、複数プロセスの公開でも整合性を維持する。

移行はトランザクションで行い、旧正常コメント・空の成功・取得日時・要求履歴を引き継ぐ。
旧キャッシュに番組単位の記録がなくても、coverageの和集合から再利用できる範囲を判断する。
旧区間の終了から24時間以上後の取得なら通常保存、それより早ければ暫定保存として移す。
暫定範囲の再確認期限は番組・固定枠へまとめ、旧実装の毎時失効を引き継がない。
細切れの18区間はそのまま利用し、現在の番組の穴を包む1要求で補完する。
正常応答が0件という理由だけで旧行を破棄しない。
既知の旧形式の変換はローカルで行い、未知形式や破損を黙って全削除しない。

## 11. 実装と検証

1. メタデータの受渡しと取得計画を純粋なロジックとして実装し、時計対応から切り離す。
2. TSの常時全編走査を取り除き、予算内の読取りでシーク・番組表示を成立させる。
3. 番組単位の補完、確認履歴とDB移行、必要時だけ動く取得ワーカーを実装する。
4. 重複統合と容量整理、取得状況・対象番組の再取得操作を接続する。
5. 以下の通信回数・I/O・表示条件を確認してから、現行仕様を新仕様へ更新する。

| ケース | 受入条件 |
| --- | --- |
| 終了から24時間以上の114分番組、空キャッシュ、正常応答 | 番組と余白を1要求で取得。途中・末尾へのシークと再起動後のHTTPは0件 |
| 同じ番組、旧18区間のキャッシュ | 最大1要求で補完。既存コメントを途中で消さず、重複分を二重表示しない |
| 現在番組が前番組、次番組が本編 | 先頭付近の情報だけで本編を選ぶ。末尾・全編調査待ちにならない |
| 番組終了2秒後までの録画 | 次番組のEITが現れても、保存済み余白を使い、次番組全体を取得しない |
| 低速Read/Seekと大容量の仮想TS | 初期追加12MiB、シーク追加32MiB以内。期限後は新規I/Oなし。停止中に全編を読み続けない |
| 番組情報なし | 固定枠内の移動では追加HTTPなし。境界の必要時だけ取得 |
| 2番組録画・番組延長・終了訂正 | 現在対象の変更時だけ必要範囲を補完。EITの繰返し・余白内の訂正では0要求 |
| 放送直後の取得 | 未反映の未来側を取得済みにしない。1時間ごとの再取得なし。翌日以降の確認は成功1回まで |
| 成功0件・後日の0件応答 | 空結果を再生ごとに再要求しない。旧正常コメントは保持 |
| JSON末尾のAPIエラー・途中切断・取込失敗・強制終了 | 取得済みが増えず旧データを保持。完了済み応答は再通信せず回復 |
| 連続シーク・2プロセス・表示切替 | 同じ対象を重複送信せず、送信済み結果が別の映像に混入しない |
| 整理で対象削除・再起動 | 完了印だけ残らない。必要になった対象を再取得でき、要求制限は維持 |
| 多数の同文・両出典・メモリー上限超過 | 元の出現数を保持し、重複取得で増殖しない。表示窓の上限で永続保存を欠落させない |

HTTPは模擬サーバー、時間は注入時計、ファイルは読取り量と遅延を計測できるRead/Seekで検証する。
公開APIへ繰り返し負荷をかける試験は行わない。
今回の実録画では追加読取り量、初回HTTP、取込、時計確定、最初の表示を別々に計測する。
ローカルキャッシュと時計が揃ったシークは、表示データ更新まで100msを目標にp95を測定する。
ネットワーク待ちやTSの時計待ちをこの数値から隠さず、別の所要時間として報告する。

実装時のコマンドとGUIの機器要件は[開発手順](development.md)に従う。
実装は上記の取得・保持・TS入力・設定UIを更新している。
