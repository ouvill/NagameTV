# 実況過去ログの取得・保存仕様

2026-09-19実装。作業ブランチ: `design/comment-archive-fetch-policy`。
有志運営のAPIに対し、同じデータの取得・走査を繰り返さないことを優先する。
以下の待機時間や保存量はアプリ側の方針であり、運営者が指定した利用制限ではない。

## 取得範囲

放送日時との対応と終端を確認できた録画は、全体の未取得範囲をまとめて取得する。
例えば未取得の21:07〜22:02の録画なら55分間を1要求にする。
番組名・ファイル名・パスはキャッシュのキーにしない。同じ局・放送日時のコメントを
別の録画や再起動後にも利用できる。

[Catalog](../rust/src/transport/programs/catalog.rs)が実際に走査した時計区間を使う。
ファイルの概算長、EPGの予定終了、未走査の空白をまたぐ時計の外挿では全体を確定しない。
同局の番組変更だけでは要求を分けず、時計対応の未確認部分は取得範囲へ含めない。
全体未確定の録画とライブの振り返りでは、確認済みの現在位置周辺を最大30分取得し、
保存済み範囲の終端の60秒前から次を取得する。30分は補助的な取得量で、DBの管理単位ではない。

DBは実際に取得したUTC秒の半開区間 `[start, end)` を持つ。固定30分枠は設けない。
必要な範囲から取得済み区間の和集合を引き、残る連続区間だけを要求する。

| 保存済み | 次の動画 | 追加する範囲 |
| --- | --- | --- |
| 22:10〜22:15、22:20〜22:30 | 22:12〜22:25 | 22:15〜22:20 |
| 同上 | 20:13〜22:50 | 20:13〜22:10、22:15〜22:20、22:30〜22:50 |

分かれた未取得範囲は現在位置を含むものから順に取得する。待機中はJobをためず、
その時点の需要とDBから次の1件を決める。APIの最大3日を超える範囲だけは分割する。
公開APIが終了秒を含むため、`starttime=start`、`endtime=end-1` を送る。
開始秒と終了秒を異ならせる必要があり、1秒だけの穴は確認済み範囲内の隣接1秒を含める。
この場合だけ保存済みの1秒と重複し得る。確認範囲全体が1秒しかなければ要求しない。
コメント自身のマイクロ秒時刻は保持する。

ライブの最新位置では過去ログを取得しない。振り返りでも、同じ時計区間でライブ受信・保存が
完了した範囲は差し引く。切断・受信キューの滞留・実況OFF中は受信済みにしない。
弾幕表示OFFでは新規過去ログ取得を止め、ライブ受信と保存は続ける。
実況機能自体をOFFにした場合は受信も止まるが、保持中のTSに対応する保存済みコメントは残す。

## 直近の放送と要求の制限

取得可能な終端は `floor((現在UTC秒 - 600) / 300) * 300`。
現在12:27なら12:15までとし、それより新しい部分を空の成功として記録しない。
直近10分が経過しても、提供元での収集完了を保証するものではない。

| 条件 | 処理 |
| --- | --- |
| 取得済みの確定区間 | 新規HTTPなし。表示位置周辺をSQLiteから読む |
| 正常応答が0件 | 空の取得済み区間を保存する |
| 区間終了から24時間以内に取得した結果 | 暫定扱い。取得から1時間後以降、必要なときだけ再確認 |
| 区間終了から24時間以上経過して取得した結果 | 通常の再確認なし |
| 要求開始 | 同じキャッシュ領域・提供元で30秒以上あけ、直近10分に最大6回 |
| 同時取得 | OSのファイルロックでプロセスをまたいで1件 |
| シーク | 出力位置確定後500ms待ち、未送信の対象を最新位置に置き換える |
| 通信断・無通信タイムアウト・5xx・429 | 5→10→20→30分待機し、0〜30秒の揺らぎを加える |
| その他の4xx・不正JSON・APIエラー | 30分と揺らぎの待機 |
| Retry-After | 指定日時／秒数と通常の待機の遅い方を採用 |
| 保存先の障害 | 保存失敗を表示。新規HTTPを止め、5秒間隔でローカルの回復を試す |

待機期限と要求開始記録はDBに保存する。選局、表示切替、再起動、キャッシュ削除で
制限を解除しない。起動中は単調時計を使い、再起動時に壁時計が巻き戻っていれば
DBに記録された時刻まで要求枠を補充しない。接続は5秒、応答開始・無通信は30秒で
タイムアウトする。受信が進んでいる応答に総所要時間の上限は設けない。
リダイレクトやHTTPライブラリー内の自動再試行も無効にする。

送信済みのGETは、シーク・選局・停止・表示OFFで中断せず保存まで完了させる。
描画には現在のソース・局・時計の照合を行い、以前の動画の結果を直接表示しない。
アプリ終了ではワーカーを停止して終了を待つ。正常に受信完了したファイルは次回回復できる。

## 受信から公開まで

[cache](../rust/crates/viewer-comments/src/cache/mod.rs)が保存と取得を所有し、
[Replay](../rust/src/features/comments/replay.rs)は需要と描画用データを所有する。
保存ワーカーと取得ワーカーを分け、HTTP待ちの間もライブ保存を進める。
ファイル操作・SQLite・解析はQtスレッドでは行わない。

1. 提供元ロックを取り、受信完了ファイルの回復を新規HTTPより先に処理する。
2. キャッシュ・頻度制限を再確認し、消費済みの要求枠と対象を持つ`EligibleRequest`を発行する。
3. この値を消費して一時ファイルを準備し、応答を`response.part`へ逐次保存する。
4. EOF・ファイル同期後に`response.json`へ変更し、受信完了を記録する。
5. ファイルを逐次検証し、正常なAPI応答とJSON全体の終端を確認する。
6. 再度逐次解析し、512件ずつ短いトランザクションで未公開領域へ取り込む。
7. 最後のトランザクションで旧区間を置換し、新コメントと取得済み区間を同時に公開する。
8. コミット後に一時ファイルと完了記録を削除する。

`Receiving`→`Downloaded`→`Validated`の所有値で順序を制約する。
末尾にAPIエラーがある応答、途中のJSON、検証失敗を空の成功として公開しない。
途中まで取り込んだ行も公開前は検索に現れず、既存の正常キャッシュは維持する。
再確認で区間の中央だけを更新するときは、前後を分割してコメントと取得日時を残す。

DBへの取込み失敗では、受信完了ファイルを残してローカルで再処理する。
ファイル名変更と完了記録の間の障害も回復対象にする。
DBへの反映済みIDを照合するため、コミット直後の終了で二重投入しない。
**応答の32MiB・10万件等の総量上限は設けず、大きさを理由に打ち切って分割再取得しない。**
保存先を使えないときは保存失敗とし、小さい範囲への取り直しには変換しない。

解析器は64KiBの入力バッファーを使い、コメントを1件ずつ扱う。
未知の大きなJSON値も全文をメモリーに保持しない。個々のプロトコル要素が既存の64KiB上限を
超えた場合はその要素を読み飛ばす。これは応答全体の停止条件ではなく、他のコメントは保存する。
表示には現在位置の16秒前から120秒先までを読み出す。
DBからの作業用保持は16MiB・5万件、描画用の投影は8MiB・2万件までとし、
この上限でディスク上の取得済みデータを削除しない。
ライブと過去ログは投稿内容・元時刻・利用者情報を照合して出現回数ごとに重複を統合し、
同文・同時刻の別投稿と自分の投稿の識別を保つ。

## DBと保持期間

保存先はOSのアプリ用キャッシュ領域の`nagametv/comment-archive/cache.sqlite3`。
Linuxは絶対パスの`XDG_CACHE_HOME`、未指定なら`$HOME/.cache`を使う。
Flatpakも自身のXDG領域に従う。Windowsは`LOCALAPPDATA`、macOSは`Library/Caches`の
パス決定を設けているが、今回の実行検証はLinuxのみ。
SQLiteは`rusqlite`の同梱版を使い、システムSQLiteの追加導入は不要。

[スキーマ](../rust/crates/viewer-comments/src/cache/schema.sql)はバージョン1。
現在の過去ログ提供元用DBを1つ置き、局・録画ごとには分けない。

| テーブル | 内容 |
| --- | --- |
| `coverage` | 実際の局・開始／終了・取得日時・最終利用・公開状態・応答ID。0件でも保存 |
| `comments` | 所属区間・マイクロ秒時刻・本文／装飾／元識別情報。1件1行 |
| `sessions` / `pins` | 生存中の再生セッションと、整理から保護する録画・ライブの範囲 |
| `live_comments` | TSセッションの受信済み投稿と、時計区間・映像時刻・自分の投稿かどうか |
| `live_coverage` | 時計区間ごとの連続して受信・保存できた時間範囲 |
| `provider` / `requests` | 待機期限・失敗回数・削除世代・更新番号と要求開始履歴 |

局・区間・投稿時刻の索引で交差区間と必要な投稿だけを検索する。
SQLiteはWAL、同期FULL、接続あたり2MiBのページキャッシュ、mmapなし、
ソート用一時領域はディスクを使う。整理時にチェックポイントと空きページ回収を試す。
未知のDBバージョンや破損を空のキャッシュとして作り直さず、保存失敗として停止する。

未使用の過去ログは、保存ペイロードと行ごとの見積りを基に256MiB・1,024区間を目安に
最終利用の古い順で整理し、30日使わなかった区間も削除する。
再生中の録画で必要な全範囲は保護し、先頭や末尾を容量目安で削除して取り直すことはしない。
同じ範囲を別プロセスも利用していれば最後の利用が終わるまで保護する。
セッションごとのOSロックで異常終了を検出し、次の起動時に古い保護とライブ保持を回収する。

ライブコメントは、**実際にタイムシフトできる全区間と先頭の16秒前まで**保持する。
TS側の保持範囲が前進・縮小した後に追従する。UTCの下限だけで削除せず、映像時刻と
時計区間を使うため、放送時計が巻き戻っても再生可能な投稿を期限切れにしない。
時計との対応がまだ確定しない投稿は保持し、対応が一意に確定してから関連付ける。
元TSを破棄する停止・選局でそのセッションのライブ保持を解放する。

ライブ保存の待機キューは8MiB。保存できるまでは受信バッチの所有権を維持し、
空きがなくなればWebSocket側のキューを新たに取り出さない。
接続断や保存待ちを連続受信済みとして記録せず、既存の保護データを黙って削除しない。
既存のWebSocket受信キューが過負荷で投稿を取りこぼした場合も、受信世代を切り替えて
その空白を連続受信済みとして扱わない。

設定の「保存済みコメント」にはDB・WAL・受信ファイルの実ファイルサイズの合計を表示する。
保護中の録画・ライブ・一時ファイルは256MiBの予算外なので、全使用量の上限とは表示しない。
「未使用のコメントを削除」は保護されていない過去ログの行だけを削除し、
要求履歴・待機期限・ライブ保存を残す。削除世代より古い取得結果は、現在も保護が必要な
場合を除いて再公開しない。物理サイズの減少はSQLiteの空きページ回収にも依存する。

## 検証

公開APIへの試験要求は行わず、合成JSON、ローカルHTTP、一時ディレクトリー、
注入した時計・SQLiteの保存失敗で確認する。機器不要のコメント単体試験:

```sh
CARGO_TARGET_DIR=build/cargo cargo test --manifest-path rust/crates/viewer-comments/Cargo.toml --release --locked --features network --lib
```

主な回帰試験は、可変区間の差分、全体1要求、先読み境界、暫定結果の置換、0件の保存、
要求制限の再起動・削除後の維持、提供元ロック、受信完了からの回復、保存失敗後のローカル再処理、
送信後のソース切替、HTTP待ち中のライブ保存、UTC巻戻りと16秒の保持である。

120,001件・32MiB超のContent-Lengthなしの応答を1要求で保存し、最後の投稿をDBから読み出し、
同じ需要の追加HTTPがないことを確認する。gzipと、受信が進みながら10秒を超える応答も試験する。
ライブは6万件・16MiB超を保存し、メモリーの件数・容量を超えても先頭と末尾を読み戻せること、
TS範囲の前進によって初めて期限切れになることを確認する。
2026-09-19の単独試験では、応答55,209,363バイト（約52.7MiB）、最大RSS 11,096KiB、
受信・検証・DB取込み・確認を含む所要時間5.48秒だった。10ms間隔で観測したDB・WAL・
受信ファイル等の最大合計は143,394,118バイト（約136.8MiB）。ファイルサイズの標本値であり、
ファイルシステムの実割当量やSQLite内部一時ファイルを含む厳密なピーク値ではない。
これはQtや映像再生を含まない受信・保存経路の試験で、公開サービスのCPU負荷の実測でもない。

アプリのRust試験、Qt通知、製品Main.qmlの起動、設定部品の試験は[開発手順](development.md)を使う。
GUI試験は[専用環境](gui-test-environment.md)で実GPU・専用画面・仮想音声を検証してから実行する。
実行結果はアプリのRust試験250件成功（手動試験3件除外）、コメント単体65件成功
（公開サービス用の手動試験1件除外）、QML部品248件成功（条件付き18件除外）。
Qt接続確認、製品Main.qmlの起動・録画／タイムシフト・終了、日本語表示の試験も通過した。

`RUST_LOG=comment_archive=debug`で完了した応答の局・範囲・保存バイト数・受信時間を記録する。
コメント本文や利用者IDはこの診断ログへ出力しない。

## 取得方針の根拠

[運営の案内](https://jikkyo.tsukumijima.net/)では5分ごとに収集し、処理にさらに約3分かかる例がある。
最大取得期間は3日だが、推奨量や推奨頻度とは解釈しない。
公開コードの確認時点
[`bca86ff`](https://github.com/tsukumijima/jikkyo-api/blob/bca86ffe77edb61d23fdf478c9aa35faca161753/app/Models/Kakolog.php#L63)
では、対象日ごとのファイルを取得・走査して要求期間を抽出している。
小さな時間区間を繰り返し要求するより、必要な連続区間をまとめた方が走査の繰り返しを
減らせると推測してこの方針にした。稼働版との一致や適切な頻度は未確認で、運営者への連絡はしていない。
運営者から別途利用方法の案内があれば、それを優先して調整する。
