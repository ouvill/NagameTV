# 実況過去ログの取得・保存仕様

2026-09-20更新。[取得・保持の再設計](comment-archive-redesign.md)を実装した現在の動作。
以下の時間・容量は、APIの最大3日という制限を除き、アプリ側の方針である。

## 番組単位で取得する

録画はTSのEITから番組開始・継続時間を読み、番組に前後2分を加えた範囲を取得する。
先頭が前番組の末尾の場合は、時計から2分以内に始まる連続した次番組を選ぶ。
番組情報の初期探索が終わる前に前番組を先行取得しない。末尾ののりしろで次番組のEITが
現れても、取得済みの余白を使う。6時間を超える番組は6時間ごとの区間に分ける。

番組情報がなければ、UTCの毎時00分・30分を境界とする30分枠に前16秒・後2分を加える。
境界の2分前から次の枠も対象にする。位置の毎秒更新では枠の起点を動かさない。
録画全編の時計確認は前提にしない。表示への同期は、現在位置で観測したTOT/TDTとPCRを別途使う。
EITの予定時刻や概算シーク位置で未読区間の時計を外挿しない。

対象内の取得済み範囲を調べ、複数の穴があれば最初から最後までを1要求にする。
古い細切れキャッシュが18区間あっても、穴ごとに18回通信することはない。
取得元はニコニコ実況とNX-Jikkyoの統合過去ログAPI。出典を保持し、各サービスに二重要求しない。
DBはUTC秒の半開区間`[start,end)`、APIには`starttime=start,endtime=end-1`を渡す。

## 再取得と通信制限

| 条件 | 動作 |
| --- | --- |
| 対象終了から24時間以上後に正常取得 | 容量整理または手動操作まで再利用 |
| 対象終了から24時間未満に正常取得 | すぐ再利用し、24時間経過後に必要となった時点で1回再確認 |
| 正常応答0件 | 空の取得済み範囲として同じ規則で再利用。旧正常コメントは消さない |
| 放送直後 | `floor((now−600)/300)*300`まで取得。保存終端の2分前に接近したとき、または対象末尾が取得可能になったときだけ追加 |
| 手動再取得 | 選択中の対象を1回更新。連打をまとめ、既存コメントを表示し続ける |
| 一時的な通信失敗 | 初回後5分、次回後30分に再試行。さらに失敗した対象は自動取得停止 |
| 不正JSON・APIエラー・非一時的4xx | 自動反復を止める |
| 保存障害 | 新規HTTPを止め、ローカルで回復を試す |

要求は同じキャッシュ領域・提供元で同時1件、開始間隔30秒以上、10分に最大6件。
失敗時の提供元待機には揺らぎを加え、`Retry-After`の長い方を守る。
対象の失敗回数、提供元待機、送信履歴は永続化し、手動操作・再起動・キャッシュ削除でも
提供元の制限は解除しない。接続5秒、応答開始・無通信30秒。進行中の受信に総時間上限はない。
HTTPライブラリーの隠れた再試行とリダイレクト追従は無効。

新規HTTPだけシーク確定後500ms待つ。キャッシュ読出しには待機をかけない。
送信済みGETはシーク・別ソースへの切替・表示OFFでも保存まで進め、独立した保持権を持つ。
データがあるかの判定だけで「取得中」にせず、通信中・取込中・次回待機・停止を区別する。

## 保存・回復・整理

[取得計画](../rust/crates/viewer-comments/src/cache/plan.rs)、
[通信](../rust/crates/viewer-comments/src/cache/download.rs)、
[応答の検証と回復](../rust/crates/viewer-comments/src/cache/spool.rs)、
[SQLite](../rust/crates/viewer-comments/src/cache/store.rs)、
[表示への投影](../rust/src/features/comments/replay.rs)で責務を分ける。
UIは最新の需要・スナップショットだけを交換し、ファイル／SQLite／HTTP処理を行わない。

応答はディスクへ逐次保存し、JSON全体・API成功を検証してから未公開領域へ取り込む。
最後に正常コメント・取得済み範囲・再確認履歴を原子的に公開する。受信完了ファイルは
ローカル取込失敗や再起動後にも再通信せず回復できる。未完了応答は成功にしない。
同一時刻・出典・内容等が同じ投稿は、各応答内の出現数の最大を保持する。
同文投稿を1件に潰したり、重なる取得で倍増させたりしない。番号の一意性は仮定しない。

表示用読出しは書込みを伴わず、取込中も公開済みデータをWALから読む。
メモリー上の表示窓・描画件数制限で永続保存を間引かない。
保存容量の既定目標は1GiB、設定範囲は64〜65536MiB。未使用日数や区間数だけでは削除しない。
古い番組・固定枠から整理し、開いている対象・送信／取込中の対象・ライブ保持は保護する。
これは論理データ量の目標で、保護中データ・SQLite索引・WAL・一時応答のため実容量は超過し得る。
設定には実使用量、「未使用キャッシュを削除」「この番組の実況を再取得」を別々に表示する。

DB形式1から2への移行はトランザクション内で行い、コメント、空の成功、取得日時、要求履歴を維持する。
既知の旧区間は再利用し、不足分のみ対象単位で補完する。コピーされた旧DBの手動削除は不要。

## TSの読取り

全編のバックグラウンド走査は行わない。非同期の形式検査を含め初期追加読取り12MiB以内、
シーク探索とSI補完の合計32MiB以内。いずれも開始2秒後から新しい探索I/Oを出さない。
形式検査済みのprefixを再利用し、通常の再生Readerが読んだ番組・時計・索引を共有する。
一時停止中に補助探索が完了した後は、追加読取りを続けない。
OSで既に実行中のファイル操作を2秒で強制中断する保証はない。

## ライブとの関係

最新位置はWebSocket受信を使い、過去ログを取りに行かない。振り返りは同じ局・時計区間で
実際に受信・保存した範囲を再利用し、不足する固定枠だけTSの保持範囲内で取得する。
ライブコメントはタイムシフト可能な範囲と先頭16秒前まで保持する。
弾幕OFFは新規過去ログ取得を止め、ライブ受信・保存は続ける。実況機能OFFは受信も止める。
録画でも弾幕スイッチは操作可能で、取得・時計待ちを無効化表示にしない。

検証方法と受入条件は[再設計文書](comment-archive-redesign.md#11-実装と検証)を参照。
