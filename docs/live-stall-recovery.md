# ライブ出力停止の検出と復旧

ライブの同じ局を視聴中、映像または音声の入力が届くのに出力が進まない場合は、
入力と再生パイプラインを作り直す。録画、一時停止、シーク、バッファリング、
過去の保持区間の再生は自動復旧の対象から外す。GPU・デコード方式は変更しない。
実放送の地方／全国切り替えの原因確定と、原因に依存しない停止検出を区別する。

## QML公開API

2026-11-12に固定した契約。以下は `Player` の読み取り専用プロパティーで、
変更通知は共通の `live_recovery_changed` を使う。通知前に全値を確定する。

| API | 型 | 内容 |
| --- | --- | --- |
| `live_recovery_state` | `QString` | `idle`（通常・対象外）、`recovering`（同じ局へ自動復旧中）、`failed`（自動復旧を終了し手動操作待ち） |
| `live_recovery_message` | `QString` | Rust側で翻訳した案内。`idle` では空文字列 |
| `retry_live_recovery()` | invokable、戻り値なし | `failed` のときだけ、失敗した同じ局で新しい視聴試行を始める。別の選択局へ移動しない。他の状態では何もしない |

日本語文言は `recovering` で「映像・音声が停止したため、同じチャンネルに再接続しています…」、
`failed` で「映像・音声を復旧できませんでした。再試行してください。」とする。
英語文言はそれぞれ “Video or audio stopped. Reconnecting to the same channel…”、
“Could not restore video or audio. Please retry.” とする。既存の翻訳カタログと
言語切り替え経路を使い、QMLでエラー文字列や再試行回数を解釈しない。

`recovering` は新しい出力の進行を確認するまで維持する。再接続の開始だけでは解除しない。
復旧回数・期限の上限、再開始の失敗、停止処理の失敗で `failed` にする。
手動再試行、明示的な再生・選局・停止、録画への切り替えで前の復旧状態を解除する。
通常のHTTPエラー表示と、既存の録画用 `recording_reconnecting` はそれぞれ維持する。

QML側では `recovering` の案内と、`failed` の案内・再試行ボタンを表示する。
### 画面での表示

[`LiveRecoveryNotice.qml`](../rust/qml/LiveRecoveryNotice.qml)が映像中央に案内を出す。
`recovering`は0.7秒続いたときだけ回転表示と文言を出し、すぐ戻る復旧では画面を乱さない。
`failed`はすぐに文言と「再試行」を表示し、再試行は`retry_live_recovery()`を呼ぶ。
文言はRustの`live_recovery_message`をそのまま表示し、QMLで状態や回数を解釈しない。

リモコンだけで使う場合に備え、`failed`になった時点で映像にフォーカスがあり、ポップアップが
開いていなければ「再試行」へフォーカスを移す。決定で再試行し、戻る・Escで映像へ戻る。
パネルやポップアップの操作中はフォーカスを奪わない。

## 検出条件と閾値

`playback::live_recovery::Recovery` はQt・GStreamerに依存しないRust型で、現在時刻と
観測値を引数で受け取る。状態は監視中、次の復旧を待機中、復旧の出力確認中、失敗のenumで表す。
入力世代が変わると観測を取り直し、以前の世代の出力で復旧を完了しない。

| 条件 | 値・理由 |
| --- | --- |
| 入力の継続 | 選択サービスのPMTに含まれるAVのPESが直近2秒以内に進行。HTTPの生バイト、nullパケット、SIだけの受信は根拠にしない。短い受信の揺れを許容する |
| 出力停止 | PMTが予告する映像・音声それぞれのsinkの `rendered` が8秒間変わらない。もう片方が動いていても検出する。通常のGOP待ちと短い構成更新に余裕を置いた初期値であり、実放送の統計から求めた値ではない |
| 復旧間隔 | 開始から次の開始まで30秒以上。短い連続障害で入力・デコーダーの再構成を繰り返さない |
| 回数 | 明示的な視聴試行につき最大3回。成功しても同じ試行の回数は戻さない。長時間の障害を無制限に隠さない |
| 復旧確認 | 開始から20秒以内に、同じ新入力世代の受信と、予告された各出力の進行を確認する。既存の受信タイムアウト15秒より長く設定する。確認できなければ、その時点で失敗を公開する |

閾値到達前に出力が動けば監視を継続する。間隔待ち中に出力が戻れば再接続を取り消し、
入力が止まった場合も停止復旧を取り消す。回数上限または確認期限を超えたら入力を停止し、
`failed` と既存の再生エラーを公開する。新規開始・停止処理の失敗もログと失敗状態へ反映する。
手動再試行は新しい視聴試行として回数をリセットする。

一時停止、利用者のシーク、保持区間の振り返り、録画、停止中は監視しない。
振り返りの判定には操作の意図を保持し、受信端と停止した出力位置の差だけでは判定しない。
「ライブに戻る」と倍速での追いつきが完了したら監視を再開する。ネイティブの
バッファリングと初期プリロールは停止判定から外すが、自動復旧の20秒期限は維持する。

出力の観測対象はGStreamer sinkの処理である。Qtが物理画面へ画像を提示したことや、
スピーカーが鳴ったことを証明するカウンターではない。デスクトップ全体やQtイベントループが
停止し、既存のPlayer poll自体が呼ばれない障害はこの監視だけでは復旧できない。

## 復旧と診断の所有者

受信側のIndexが最新のPMT版・PCR PID・ESのPID／stream_typeとAVの入力カウンターを持つ。
Playbackは映像sinkと実際の音声sinkの出力カウンター、および最大24件のGStreamer bus履歴を持つ。
履歴には状態変更・構成選択・buffering・warning/errorのドメインとコードを記録し、
外部のエラー本文やURIは追加しない。停止を処理するときに入力・出力時刻、カウンター、
構成、bus履歴を `tracing` の標準エラーへ一度記録する。保持状態の描画ではログを出さない。

Playerアダプターがコアから一度だけ使える復旧許可を受け取り、停止完了後に同じ局の入力を
作り直す。playbinをREADYへ戻し、appsrc・TS保持領域・Reader・tsreadex・字幕世代を更新する。
既存の映像sinkとGPU設定は維持する。復旧時はその局のライブ位置から再開し、前の履歴を破棄する。
保存した局の識別情報を使うため、手動再試行を別の選択局へ読み替えない。
既存のHTTP Range拒否に対する一度だけの復旧許可を、停止復旧によって再付与しない。

## 合成TSと再現手順

新しい5素材は放送コンテンツを含まない。`recording.ts` と `media-h264.mp4` を元に、
3秒のMPEG-2/AACから構成を切り替える。H.264は既存MP4からデコードせず再muxする。
版・PCR・音声・サービスの素材は3区間、codec素材はMPEG-2の3秒とH.264の12秒で構成する。
区間の時刻は3.2秒ずつずらし、連続性カウンターをつなぐ。新素材では不連続フラグを加えず、
既存の時計リセット素材と区別する。

| 素材 | 変更 |
| --- | --- |
| `live-transition-version.ts` | 同じESのままPMT版0→1→2 |
| `live-transition-pcr.ts` | PCRを映像PID `0x41` から専用PID `0x1fe` へ移し、元へ戻す |
| `live-transition-audio.ts` | 第2 AAC `0x43`／コンポーネントタグ `0x11` を追加し、削除する |
| `live-transition-service.ts` | PAT/PMTのサービス1を2へ変更し、1へ戻す。選択サービスの一時消失 |
| `live-transition-codec.ts` | 映像PID `0x41` を維持し、stream_typeをMPEG-2 `0x02` からH.264 `0x1b` へ変更 |

再生成は `python3 tests/fixtures/generate_live_transitions.py`。
Python標準ライブラリーとGStreamerのmux/parserが必要で、表示・GPU・音声機器を使わない。
既存のPID変更・時計リセット・字幕／第2音声追加の3素材も同じ比較に含める。

```sh
python3 scripts/test.py app --profile release --filter 'test(playback::live_recovery::) | test(playback::input::live_transition_tests::) | test(playback::input::stall_recovery_tests::) | test(player::stream_state::)'
python3 scripts/test.py connection localization --profile release
```

機器不要の比較は元TSと共通入力のReaderを同じplaybin3、明示的なCPUデコーダー・メモリーsinkで
再生する。製品のデコード方式は変更しない。PMT構文・CRCと各構成を検証し、EOFだけでなく
切り替え後の映像・音声バッファーも要求する。生TS側の結果は比較用に記録し、時刻・フレーム数が
実行順序に依存するため固定値にはしない。

停止復旧の結合試験はローカルHTTPで音声追加素材を逐次送信し、PMT変更後に映像sinkへの
バッファーを破棄して出力停止を注入する。入力とデコードは実処理を使い、ポリシーの時刻だけを
進めて、同じ `/api/services/1/stream` への2回目の要求と新しい映像・音声出力での復旧を確認する。
これは障害後の復旧機構の試験であり、放送切り替えが同じ障害を起こす証拠ではない。
単体試験では閾値ちょうど、片方だけの停止、無信号、音声だけのサービス、操作による除外、
回数・間隔・確認期限・明示的なリセットを確認し、操作列をproptestでも検査する。
QML通知中に停止や選局が受け付けられた場合は、取り消された復旧要求を適用しない。
接続試験でも復旧中・失敗通知からの停止が古い要求や不要なエラーを残さないことを確認する。

実GPUの製品Main.qml試験は既存の `startup` 公開入口を使う。初期状態の公開値と
通常時の再試行が何も変更しないことも同じ起動試験で確認する。
EOFやCPUメモリー出力の成功を、実GPU・音声出力の検証結果に読み替えない。

### 実放送TSの比較入口

録画経路は `python3 scripts/test.py startup --profile release -- recording-probe TS_PATH [SECONDS]`、
ライブ経路は `python3 scripts/test.py startup --profile release -- live-probe SERVER SERVICE_ID [SECONDS]`
で比較する。両方とも専用画面・実GPU・仮想音声の検証後に製品Main.qmlを使う。
両診断とも既定28秒、最大600秒の間、映像出力が6秒を超えて止まらず、再生・入力エラーや
自動復旧への移行がないことを確認する。ライブ診断は指定サービスだけを選局し、
データ放送と実況を無効にする。
短い素材では、観測時間と初期バッファー分を含めて配信が続くように時間を指定する。

実受信TSをローカルHTTPで配信する場合は、元のPCRに合わせて送信を制御し、
パケット・PID・タイムスタンプを書き換えない。サービス一覧には実際のnetworkIdとserviceIdを使う。
この診断は配信サーバーを内蔵しないため、入力条件とHTTP要求回数は配信側でも記録する。
復旧状態の標本だけで瞬間的な再接続まで否定せず、ストリーム要求が1回であることと
GStreamerログを照合する。ローカル配信はチューナーの受信断や実ネットワークの揺れを再現しない。
