# NX-Jikkyoの通信と再試行

2026-09-22更新。NX-Jikkyoへのライブ受信・勢い／番組情報取得・投稿接続の現行仕様。
以下の待機時間はアプリ側の設計値で、提供元の要求上限を示すものではない。

## 通信の対象と状態の寿命

アプリの`Network`がNX-Jikkyo専用の`service::Client`を所有する。
ライブ受信、勢い／番組情報取得、投稿はそれぞれ失敗回数と待機期限を持ち、
429などによる提供元全体の待機期限を共有する。

| 操作 | 接続先 | 通信の起動条件 |
| --- | --- | --- |
| ライブ受信 | `/api/v1/channels/jk{id}/threads`と`/api/v1/channels/jk{id}/ws/comment` | 実況が有効で対応局が選ばれているとき。スレッド一覧取得後にWebSocketを購読 |
| 勢い・番組情報取得 | `/api/v1/channels` | 実況が有効で局一覧があるとき。録画再生中や一覧非表示でも対象 |
| 投稿 | `/api/v1/channels/jk{id}/ws/watch` | 利用者の送信操作ごとに接続。詳細は[コメント投稿](comment-posting.md) |

待機期限と失敗回数は選局や実況ON/OFFで解除しない。保持期間は同じクライアントが存在する
アプリ起動中で、再起動をまたいだ永続化や別プロセスとの共有は行わない。
過去ログAPIは別の取得処理を使うため、[過去ログの取得・保持](comment-archive-redesign.md)を参照。

## 一時障害の待機時間

通信断・タイムアウト・HTTP 408・5xxは一時障害として扱う。
ライブ受信の通常切断も再接続の対象となり、短時間の接続と切断が続けば待機を延ばす。
スレッド一覧や勢い応答の解析失敗も、該当する取得処理の待機延長に含める。
表は同じ種類の障害が続く場合の基準秒数である。

| 操作・応答 | 基準秒数の推移 |
| --- | --- |
| ライブ受信の一時障害・通常切断 | 5 → 10 → 20 → 40 → 80 → 160 → 300、以後300 |
| 勢い・番組情報取得の一時障害 | 60 → 120 → 240 → 300、以後300 |
| HTTP 429 | 初回から60以上。429が続く場合は60 → 120 → 240 → 300、以後300 |

失敗回数は操作ごとに数える。同じ操作で5xxと429が交互に届いても回数を引き継ぐ。
429では`Retry-After`が欠落・不正でも、基準秒数を最低60秒として計算する。

### Retry-Afterとランダムな待機

`Retry-After`は秒数またはHTTP日時として解析する。HTTP日時は受信時の壁時計から
残り時間へ変換し、その後の待機判定には単調時計を使う。解析できない値はヘッダーなしと同じ扱いにする。

再試行可能なHTTP応答では、今回の待機時間を次で計算する。

```text
待機時間 = max(基準秒数, Retry-Afterの残り時間) + 0〜30秒のランダムな揺らぎ
```

通常の通信断にも同じ揺らぎを加える。300秒は基準秒数の上限であり、
揺らぎや提供元が指定した長い待機時間によって実際の待機は300秒を超える。
既にある待機期限を新しい応答で短縮しない。

429はヘッダーの有無によらず、この期限をNX-Jikkyo向けの全操作で共有する。
408・5xxに有効な`Retry-After`がある場合も共有する。
待機は新規要求と再接続の開始に適用し、確立済みのコメント受信は継続する。
期限が来ても、実況が無効など通信の起動条件を満たさなければ要求を出さない。

## 失敗回数のリセットと取得停止

ライブ受信では、購読送信を終えて受信状態に入ってから60秒以上接続が続いた場合に限り、
切断・取消し時に失敗回数をリセットする。接続直後に切れた場合は回数を維持する。
継続時間は通信タスク側で測り、GUIの更新間隔やコメントの到着件数には依存しない。

勢い・番組情報取得は正常な応答を解析できたときに、自分の操作の失敗回数だけをリセットし、
次の通常取得まで60秒待つ。投稿も対応する成功応答を確認したときに自分の失敗回数をリセットする。
いずれの成功も、他の操作の失敗回数や提供元全体の待機期限を解除しない。

400・401・403・404など、408と429以外の4xxは該当する操作・接続先を停止する。
3xxも自動追従せず停止扱いとする。停止理由を保持し、ライブ受信ではエラーとして表示する。
停止は同じクライアントの間は解除されず、アプリ再起動で初期化される。
別の実況チャンネルの接続先には、この恒久的な停止を適用しない。

## WebSocketの終了通知

視聴・投稿用の`ws/watch`ではJSONの`disconnect`通知、受信用の`ws/comment`では
WebSocketのCloseフレームを扱う。終了理由は`Termination`で保持し、
通知の理由文字列やCloseコードを再接続・停止の判断に使う。

| 通知・Closeコード | 処理 |
| --- | --- |
| 受信側の1000（正常終了） | 受信終了として扱い、待機後にスレッド一覧から現在のIDを取得して再接続 |
| watchの`END_PROGRAM` | スレッド終了として投稿試行を終える。次の手動送信にも投稿側の待機を適用 |
| `SERVICE_TEMPORARILY_UNAVAILABLE`、1011（内部エラー）、1012（再起動） | 一時障害として段階的に待機を延ばし、その期限をNX-Jikkyo向けの全操作で共有 |
| 1013（後で再試行） | 初回60秒以上の待機を全操作で共有し、連続失敗で延長 |
| 1008（ポリシー違反）、1003（未対応データ）、1007（不正なデータ） | 該当する操作・接続先を停止し、理由を保持 |
| 1002、その他のコード、コードなし、未知のJSON終了理由 | 該当操作の一時障害と同じ待機延長を適用 |

NX-Jikkyoは1002を「現在のスレッドが見つからない」「指定スレッドが開始前」などにも使うため、
このコードだけでは接続先を恒久停止しない。Closeの自由文を部分一致で分類せず、元の理由を保持する。
各待機には0〜30秒の揺らぎを加え、既存の提供元待機を短縮しない。
正常終了でも短い接続と切断が続く場合は、従来どおり待機を延ばす。

受信側はCloseへの応答を待つ前に、待機・停止と受信終了状態を公開する。
応答の送信失敗や取消しで、受け取った終了理由を一般的な通信エラーに置き換えない。
終了前にキューへ入ったコメントは既存の件数制限で渡し終え、旧接続の終了を確認してから再接続する。

投稿は本文送信前の終了を失敗、本文送信後で成功応答を未確認の終了を結果不明とする。
`END_PROGRAM`でも、送信済み本文が受理されなかったとは断定しない。
本文を自動再送せず、確認済みの成功を後続の切断で取り消さない。

参照：[NX-Jikkyoのwatch終了通知](https://github.com/tsukumijima/NX-Jikkyo/blob/d6009f524dbcc41ee94ad561a71785c1d48a0d38/server/app/routers/websocket.py#L1233-L1253)、
[コメント受信側のスレッド終了](https://github.com/tsukumijima/NX-Jikkyo/blob/d6009f524dbcc41ee94ad561a71785c1d48a0d38/server/app/routers/websocket.py#L1618-L1622)。

## 要求の開始と取消し

待機判定に通った要求だけが、対象を固定した`Authorized<T>`を取得する。
受信タスクの開始はこの値を消費する。HTTP送信直前と、スレッド一覧取得後の
WebSocket接続直前にも待機を再確認し、他の操作から届いた429を反映する。
HTTPライブラリーの自動再試行とリダイレクト追従は無効にする。

受信済みの失敗は、GUIへ結果を公開する前に共通の待機状態へ記録する。
選局や実況OFFで完了済みの結果を捨てても、既に記録した429の待機は残る。
勢い取得の完了・取消しは、未完了なら処理の所有権を返すAPIで確認する。
ライブ受信と勢い取得はそれぞれ、旧タスクの終了を確認してから次のタスクを開始する。

投稿は提供元全体の待機と投稿自身の制限を確認してから開始する。
watch接続時のHTTPエラーと接続後の終了通知を共通の制御へ反映するが、本文の自動再送や待機キューは作らない。
待機中の送信操作は受け付けず、理由を表示して下書きを保持する。

HTTPは接続5秒、要求全体10秒を期限とする。受信用WebSocketは接続・購読送信・
制御応答にそれぞれ10秒、投稿は接続から応答確認まで全体で10秒の期限を持つ。
コメントが届かないだけで受信用WebSocketを切断する無通信タイマーは設けない。
