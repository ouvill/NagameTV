# コード規約

新規実装と既存コードの変更では、変更漏れをコンパイラーが検出できる構造を優先する。
状態・前提条件・操作順序を表す場面では、`enum` と Typestate（型状態）を積極的に採用する。
型によって何を禁止できるかを明確にし、その保証を維持できる所有関係とAPIを設計する。

## 状態はenumで表す

- 同時に成立しない状態を複数のboolで表さず、enumのvariantに分ける。
- その状態で必要なデータはvariantの必須フィールドにする。
  「再生対象がないのに再生中」などの組み合わせを構築できなくする。
- 状態を追加したときに判断が必要な処理は、variantを列挙した網羅的なmatchにする。
  `_`で将来のvariantを黙って受け入れない。
- 派生値は元の状態から算出する。UI用の独立したフラグを手動で同期しない。

例: [再生状態](../rust/src/player/stream_state.rs)、
[番組表の状態](../rust/src/features/program_info/guide.rs)。

## 操作の前提条件と順序はTypestateで表す

- 初期化、検証、開始、取消し、停止など、前段階の完了が必要な操作では、
  完了を証明する型を受け取るAPIを優先する。
- 状態遷移では`self`を消費して次の型を返すか、対象を排他的に借用する短命の型を返す。
  一度しか使えない権利にはClone/Copyを実装しない。
- 非同期操作は、未完了なら操作の所有権を返し、完了なら結果を返す。
  終了確認と結果取得の順序を各呼び出し元に覚えさせない。
- 検証済みの型は、検証に成功した経路だけで構築できるようにする。
  privateなフィールド・コンストラクターを使い、汎用的な可変参照や無検証の変換で
  保証を迂回できないようにする。
- 確認した対象と結果を同じ値で運ぶ。URL・処理世代・資源の対応を失う独立した
  boolや、任意の対象へ流用できる「完了トークン」を作らない。

例: [Jobから完了結果への遷移](../rust/src/services/job.rs)、
[接続確認](../rust/src/services/server.rs)、
[起動時設定から実行中設定への遷移](../rust/src/settings/mod.rs)、
[停止済みの再生資源](../rust/src/playback/session.rs)。

## 所有と外部境界

- 一緒に更新・解放する必要があるものは、共通の所有者と操作へまとめる。
  エラー経路やDropも同じ順序を守り、停止失敗時は必要な資源を保持する。
- Qtへ複数の派生値を公開するときは、元の状態全体を更新してから通知する。
  通知中の読み取りでも整合した値を返す。
- QObjectやイベントループの現在状態にはenumを使い、その内部の個々の操作には
  Typestateを組み合わせてよい。全体を一つの巨大なジェネリック型にする必要はない。
- 外部の変化やFFIの安全条件は実行時にも確認する。接続確認済みという型が証明するのは
  その確認の成功であり、将来の接続可能性ではない。Qtが所有するオブジェクトの寿命、
  スレッド、GStreamerの状態遷移などの検証を型の名前だけで置き換えない。
- 設定ファイルや外部APIの形式と内部の型を分離し、互換性を保ったまま境界で検証する。

## レビューと検証

変更時には「次に変更する人が、何を覚えている必要があるか」を確認する。
複数の更新箇所、必須の呼び出し順序、状態と無関係に呼べる危険な操作が残る場合は、
型・可視性・所有者・操作の境界を見直す。

Optionは本当に値が不在になり得る場合に、Defaultやワイルドカードは省略・未知値を
受け入れる意味がある場合に使う。コンパイルエラーを消すためだけに必須情報を任意化しない。
enumやTypestateを使っても保証が増えない単純な値・独立した選択まで機械的に変換しない。

型で禁止した誤用はコンパイル時に検出できるAPIを保つ。テストでは、失敗・取消し・
遅れて届く結果・資源解放順序・通知中の読み取りなど、型だけでは検証できない振る舞いを
確認する。公開APIのコンパイル失敗テストを実行できる構成では、それも利用する。
RustとQMLの境界変更では、部品テストに加えて製品のMain.qmlを使う起動テストを行う。
実行手順と機器要件は[開発手順](development.md)と[Qtテスト](qt-tests.md)を参照する。
